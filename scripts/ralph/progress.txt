## Codebase Patterns

- 工具层在 `backend/app/services/agent/tools.py`，`make_tools(db, user_id, anonymous_id, ctx)` 是**每请求闭包工厂**，工具实例绑定本次请求的 db 会话与归属者。
- **`kb_search` 必须始终是 `make_tools` 返回列表的第一个元素** —— `tests/test_agent.py` 与 `tests/test_agent_tools.py` 依赖顺序。
- 归属过滤统一走 `_owner_filter(model, user_id, anonymous_id)`：登录按 `model.user_id == user_id`，匿名按 `model.user_id.is_(None) & (model.anonymous_id == x)`；识别不到身份要**明确拒绝**而不是返回全部数据。
- 工具内部**必须吞掉异常**返回自然语言兜底 —— 工具无法返回 HTTP 状态码，抛异常会让整轮 Agent 崩。
- 工具返回值是给 LLM 读的**自然语言**，必须截断（单块内容 300 字上限的先例）。
- JSONB 列写入 Python `None` 会落成 JSON `null` **字面量**而非 SQL NULL，`is_not(None)` 过滤不掉，必须再判 `isinstance(value, dict)`。
- 限额/记账复用 `usage_service.count_today_usage_by_owner(db, action_type, user_id, anonymous_id)` 与 `usage_service.write_usage(...)`，不要新写 SQL。
- 测试要在 `backend/` 目录下跑（`.env` 相对当前目录读）；新测试用专属标记只清自己造的数据，不要 `DELETE FROM` 全表。
- ⚠️ 跑全量 pytest 会清空 `kb_chunks` / `kb_documents`（老 `tests/test_rag.py` fixture 行为），跑完需 `python -m scripts.seed_kb_preset` 恢复语料。
- 前端零图表库、零 UI 框架：可视化一律手写 SVG/CSS；组件内映射表用常量 + 回落原始值（参考 `HistoryView.vue` 的 `actionMap`）。
- **准入检查只有 `ruff check .`**：`ruff format --check` 对 `tools.py` 等既有文件本来就报警（HEAD 即如此），是前格式化时代留下的。**别顺手整文件格式化**（会造出大量与 story 无关的 diff），按邻近代码风格写即可。
- 工具在 `services/` 层**不得 import `app/api/`**（项目是 Router → Service → Model 单向依赖）。需要复用接口层查询时，先把它下沉成 service 函数，接口与工具都调那一份，不要复制 SQL。
- `created_at` 是 `server_default=func.now()`（事务开始时间），**同一事务插入的多行时间戳可能完全相同**——所有「取最近 N 条」查询必须带 `id desc` 兜底排序；测试里要控制先后就**显式传 `created_at=`**（`InterviewSession(created_at=...)` 会覆盖 server_default）。
- ⚠️ 开跑 pytest 前先确认 Docker Desktop 起来了：本项目容器是**已存在但 stopped**，用 `docker start ai-interview-db ai-interview-redis ai-interview-ollama`；`docker compose up -d` 会报 name conflict。DB 没起时 pytest 会**挂住不报错**（连接超时很长），别误判成死循环。
- 知识库可见性判据是 `kb_service._visible_clause`（`scope=public` 全站可见 / `private` 仅归属者），工具与接口都复用它；但测试里造的 `scope=public` 文档 `user_id` 与 `anonymous_id` **都是空**（与预置语料同形），按归属者清理清不掉 —— 测试数据要带**标题前缀**，清理时用 `title LIKE '前缀%'` 兜底（`tests/test_agent_tools.py` 的 `_KB_PREFIX`）。
- 开发库长期有 7 篇预置语料，凡「空库 / 精确条数」类断言都会被它干扰：要么只断言与总数无关的片段（如「仅显示前 20 篇」），要么 monkeypatch 掉查询函数隔离验证。
- **纯静态工具（如 `platform_help`）用同一套「别名元组 → 文案」路由**：对 topic 与别名都做小写化再判包含，**别名顺序即优先级**（具体主题排前，防泛词抢匹配），空 topic 或全不命中回落总览；这类工具不查库，`db` 传 `None` 也能跑通。
- 工具 `description` 要三段式（做什么 / 什么时候用 / 什么时候**不**用），易撞的工具互相点名排他（如 `kb_search` ↔ `platform_help`、`resume_lookup` ↔ `analysis_read`）。
- 描述的可校验写法：统一用**中文冒号小标题**「什么时候用：」「什么时候不用：」当锚点，测试断言 `len(description) > 50` 且两个锚点都在；再加一条「参数化清单 == `make_tools` 实际返回」的测试，新增工具漏写描述会直接红。
- 改描述属于**纯 docstring 改动**，不影响任何工具行为：断言描述不需要数据库，`make_tools(None, None, None, ToolContext())` 取 `.description` 即可（与 US-005 证明静态工具不查库同一手法）。
- ⚠️ ruff 实际启用的是**扩展规则集**（含 `RUF100` / `BLE001` / `B008` / `SIM` / `S110`），但 **`E402` 未启用**：照 `scripts/eval_rag.py` 写 `sys.path.insert` 后再 import 时**不要加 `# noqa: E402`**（会被 RUF100 判为多余指令）。
- ⚠️ **`BLE001`（盲吞异常）的免死金牌是"带堆栈地记日志"**：`logger.exception(...)` 或 `logger.warning(..., exc_info=True)` 的处理器**不报**；纯 `return`/赋值/`logger.warning("x")`（无 `exc_info`）才报——`app/main.py:89`、`app/db/session.py:38` 属于后者所以才要 `# noqa: BLE001`。tools.py 里最常见的 `except Exception:` + `logger.exception(...)` + `return 文案` 写法**千万别加 noqa**（反被 RUF100 判为多余）。判据永远是直接跑 `ruff check <文件>`，别照抄别处。
- 工具内部要调模型的场景统一走 `_run_tool_llm(db, user_id, anonymous_id, call)`：返回 `(结果, 兜底话术)` 两者只有一个非空；**超限/`limit=0` 时连 `call` 都不执行**（这是省钱的关闸）；异常不在这一层吞（"JD 太短""回答为空""服务欠费"话术各不相同，由工具自己 try/except）；**成功才记账**（写 `agent_tool_llm` 并 commit）；无归属者不写账。新工具要调模型必须走它，否则限流与成本统计会漏。
- 新增 `action_type` 时记得同步 `tools.py` 的 `_ACTION_LABELS`，否则 `usage_stats` 会把英文枚举直接甩给用户。
- 写可测脚本（CLI 评测类）的套路：把「一次 LLM 调用」抽成注入的 `ask: (question) -> BaseMessage`，`run(cases, ask)` 只做纯统计；测试里用**替身模型**（只需实现 `bind` / `bind_tools` / `invoke` 三个方法返回 `AIMessage(tool_calls=[...])`）即可离线覆盖。测 `main()` 时 monkeypatch 三件套：`load_cases` / `REPORT_PATH`(tmp_path) / `build_chat_llm`。
- 路由评测只需**工具 schema**，不要执行工具：`make_tools(None, None, None, ToolContext())` 拿描述 → `build_chat_llm().bind(temperature=0).bind_tools(tools)` → 读 `msg.tool_calls[0]["name"]`；模型直接文字作答时用 `NO_TOOL` 占位计入未命中。
- ⚠️ 每新增一个工具，`data/agent_eval/routing.json` 必须同步补 3 条用例：`tests/test_eval_agent_routing.py::test_cases_cover_every_tool` 断言「用例数 ≥ 工具数 × 3」，只加工具不加用例全量 pytest 会直接红。
- 提示词版本是**每套提示词一个常量**、互不相干：`prompts.PROMPT_VERSION`（简历分析，入 analyses 表）、`interview_prompts.INTERVIEW_PROMPT_VERSION`、`prompts.JOB_MATCH_PROMPT_VERSION`。**绝不要为了"新增提示词"去递增 `PROMPT_VERSION`** —— 那会让库里所有旧分析报告按「版本过期」失效。
- 工具内调 LLM 的工具（`job_match` / `question_gen` / `answer_review`）实现套路：`_run_tool_llm(db, user_id, anonymous_id, lambda: chat_json(SYSTEM_PROMPT, build_xxx_prompt(...), settings, XxxReport.model_validate))`，**整个调用包一层 try/except 兜话术**（`_run_tool_llm` 不吞异常），AI 输出契约放 `app/schemas/agent.py`，提示词放 `app/services/prompts.py`。
- 测这类工具只需 monkeypatch `app.services.agent.tools.chat_json` 做替身（记录 `system`/`user`/`validator` 三个入参）：成功路径断言渲染文本 + 记账，短路路径（空参数/无数据/超限）断言 `seen == []` 证明一次模型都没调。
- ⚠️ **同一文件上的多个 Edit 不要并行发**：实测在同一条消息里对同一文件发两个 Edit，其中一个会静默丢失（工具回报成功但文件没变），直到 ruff/pytest 报 F821 / 断言失败才发现。改同一文件时**逐个串行改**，改完 grep 关键字确认落地。
- ⚠️ pydantic 的 `Model.model_validate` 每次取出来都是**新对象**，`is` 比较会失败（`assert X is Y` 报 "model_validate is model_validate"）；要断言"用的是哪个校验器"就**调用它**再 `isinstance(结果, 模型)`。
- 需要"先检索再喂给模型"的工具，别去 invoke 另一个工具对象：把检索链路抽成模块级公共入口（本项目是 `_kb_retrieve(db, query, user_id, anonymous_id, top_k) -> (命中块, 兜底话术)`），返回话术而非抛异常，让不同调用方自己决定处置（kb_search 要区分向量模型挂了/检索出错，question_gen 一律当"未收录"退回模型出题）。
- 混合检索（hybrid）路径**不套 `kb_min_similarity`**（设计如此，为救回纯词法命中的术语查询），所以"检索未命中"在真机上几乎不触发——连明显无关的 topic 也会返回低分材料。"未命中"分支只能靠 mock 空结果覆盖，别指望真机复现；输出里标注来源时要意识到这一点。
- ⚠️ **`backend/app/services/prompts.py` 是全仓库唯一的 CRLF 文件**（其余如 `tools.py` / 测试都是 LF）：Edit 的**多行 old_string 匹配不到**（行尾是 `\r\n`），只能用**单行锚点**替换/插入；插入多行时新行按 `\r\n` 写，别把文件搞成混用行尾。改前先 `python -c "print(open(f,'rb').read().count(b'\r\n'))"` 确认。
- 新增/改一个工具的**六处同步点**（漏一处就红）：`make_tools` 返回列表（`kb_search` 仍须下标 0）→ 模块 docstring 工具清单 → `tests/test_agent_tools.py` 的 `_ALL_TOOLS` 与 `test_make_tools_exposes_*_tools` → 易撞组合互指（双向点名 + 测试参数对）→ `data/agent_eval/routing.json` 补 3 条用例 → `docs/Agent工具设计.md` §二表格与 §四易撞表。
- 跨工具复用的评分口径直接遍历 `_SCORE_LABELS`（技术深度/表达结构/项目真实性/整体），只点评单项时 `if key != "overall"` 过滤即可——不要另起一份中文映射，会和模拟面试报告漂移。
- 工具内调 LLM 的三件套（`job_match` / `question_gen` / `answer_review`）里有两类「不需要身份」：`question_gen`（只查公共语料）与 `answer_review`（题目和回答都是用户当场贴的，不查库）——它们没有 `_owner_filter`，但仍走 `_run_tool_llm` 限额与记账。
- 测「入参截断」时填充字符要**避开提示词模板里已有的字**：「答」会撞上 `候选人的回答：` 让计数多 1（`2001 != 2000`），换模板里不存在的字（如「好」）或直接照 job_match 用例用 `x`。
- **路由评测用例必须"自包含"**：单轮评测只发一句问法给模型，凡是"我贴一段 JD…""刚才那道题我是这样答的…"这类**引用本轮看不到内容**的问法，模型正确地选择"不调用工具"会被判误选 —— 写用例时把 JD 要求原文 / 回答原文写进问句里。
- 模型"不调用工具"的三大根因（按出现频率）：① 描述里有劝退句（job_match 的"用户没贴 JD 时不要调用"让口语化岗位要求全部落空）② 用户话里的技术名词把它带跑（"Redis 缓存穿透…能得几分" → kb_search）③ 归属词误判（"这个平台" → platform_help）。修法都是在**描述里写清触发场景与反例**，而不是删参数。
- **前端没有测试框架、也没有 lint**（`package.json` 只有 dev/build/preview），质量门禁就是 `npm run build`；但 vite build **不会**校验模板里引用的函数是否存在（`<script setup>` 绑定是运行时解析），改完必须另想办法验证渲染。
- 离线验证单个 Vue 组件渲染的可行套路（无需浏览器）：`node` + `@vue/compiler-sfc`（`parse` → `compileScript`（**不要** inlineTemplate）→ `compileTemplate`）拼成一个临时 `.mjs` 写进组件同目录（相对 import 才不会断），再用 `createSSRApp` + `renderToString` 渲染。`compileScript` 必须**不带** `inlineTemplate`，否则 setup 返回的是 render 函数、拿不到绑定。
- 想改组件内部状态做渲染验证：`<script setup>` 的绑定**不允许**从 mixin/beforeCreate 外部改（Vue 会 warn 并抛 "trap returned falsish"）。正确姿势是包一层组件 `setup(props, ctx) { const b = Comp.setup(props, ctx); b.messages.value = [...]; return b }` —— 绑定对象是 ref 集合，直接改 `.value`。
- 描述校准的有效句式：「用户只用口语描述了岗位要求（例：这家公司要求熟悉 MySQL 和 K8s）**也算 JD**」「不要因为用户贴的回答里提到某个技术名词就去 kb_search」「问的是**收录范围**而非**操作入口**」——把判别标准而不是工具名写给模型，比堆砌"请用 X"有效。
- ⚠️ uvicorn `--reload`（watchfiles）在 Windows 上会**漏检后续改动**：实测 config.py 触发一次 reload 后，session/errors/main 的改动全部没被重载。改后端代码后要么 grep 日志确认 "Reloading"，要么干脆不带 --reload 手动重启；杀后端必须 `netstat -ano` 找真实监听 PID 再 `taskkill //F //T`——nohup 记的 `$!` 是 MSYS 包装进程 PID，杀它杀不到 python，会留下占 8000 的僵尸进程（且新 uvicorn 还能再绑一次 8000，netstat 出两条 LISTENING）。
- 本地 `DATABASE_URL` 主机写 **127.0.0.1 而非 localhost**：Docker 停容器时端口是"黑洞"（vpnkit 代理还收连接），libpq 对 localhost 双栈会 ::1 和 127.0.0.1 **各超时一次**（connect_timeout=5 实测 10.4s 才失败），单栈一次 5s。US-006 实测 503 耗时从 60s+ 降到 5.3s 的最后一步就是改这里。
- `connect_args` **不会**体现在 `dialect.create_connect_args` 的返回里（建连时才合并进 cparams）：要验证参数真传到了驱动，用假 `dbapi.connect`（monkeypatch 后捕获 kwargs）+ NullPool 一次性引擎，别去内省 dialect。
- DB 连接类异常的全局 503 处理器在 `app/core/errors.py` 的 `database_error_handler`（OperationalError/InterfaceError → `database_unavailable`），注册在 `app/main.py` 既有处理器区；新增基础设施类异常处理器加同一处，**不要在路由内 try/except**。
- check_env 的检查函数套路：每个 `check_*` 返回 `CheckResult`，内部 `except Exception` 转 FAIL **不上抛**；BLE001 免死金牌是 `logger.warning(..., exc_info=True)`——**带了 exc_info 就千万别再加 `# noqa: BLE001`**（RUF100 判多余，US-007 实测两次）；测试全用 `plan` 参数注入替身函数名，真实环境验证人工跑一次脚本即可。
