## 一、简历版（一屏可读，直接粘贴）

**AI 求职助手平台（个人项目）** ｜ 独立开发 ｜ 2026.08 – 至今
`FastAPI` `LangChain 1.x` `LangGraph 1.2` `PostgreSQL + pgvector` `Redis/Celery` `Ollama` `Vue 3`

**项目背景**：面向求职者构建「简历诊断 → 模拟面试 → 复盘提升」闭环工具，解决简历缺乏针对性反馈、面试练习无结构化反馈、录音复盘无工具支撑三类痛点。以「文档 + 语音」双模态输入为起点，由 LangChain / LangGraph 双轨 Agent 编排，产出结构化诊断报告与四维面试评分。

**核心工作**

1. **多模态输入解析**：PDF/Word 简历走文本抽取 + **magic bytes 文件头双校验** + hash 去重，Celery 异步解析；面试录音走 **faster-whisper 本地转写**（GPU 免依赖，支持快速档）→ LLM **角色审核**（自动切分面试官/候选人对话）→ 生成四维评分报告，把「靠回忆」的面试变成可复盘的结构化数据。
2. **双轨 Agent 编排**：v1 用 LangChain ReAct（`create_agent` + `astream_events` 流式桥）挂 **13 个工具**，每请求**闭包工厂**绑定本次 db 会话与数据归属者，杜绝多请求串数据；v2 用 LangGraph `StateGraph` 串起 `planner → load → analyzer → matcher → questioner → verifier(回环≤2) → hitl_gate → deliver`，`PostgresSaver` 断点续跑 + `interrupt` 人工审批（TTL 30min），异常可回退，两轨开关切换互不影响。
3. **RAG 混合检索优化**：段落合并切块（600 字/块 + 60 字重叠）→ pgvector HNSW 向量召回 + jieba/BM25 词法召回**双路并行** → RRF 融合排序，配合引用来源回显与兜底话术。
4. **面试官 Agent 智能追问**：逐轮评分识别回答单薄（`depth_signal=weak` 或 ≤4 分）→ 以面试官人设口吻生成针对性追问再挂起等作答；追问**不占主问题轮次**、预算可配（默认 1 次/问，0 可关）。

**量化成果**：RAG 检索 **hit@1 71.4% → 87.8%**、**hit@5 91.8% → 100%**；Agent 工具路由 top-1 **40/40 = 100%**（13 工具）；LangGraph 端到端黄金任务 **11/11**、面试图场景 **8/8**；**414 个单测全绿、覆盖率 90.3%**；依赖漏洞 **14 → 0**；Alembic **17 次迁移零漂移**。

## 二、项目背景（展开讲）

**目标用户**：准备秋招/社招的求职者。
**三个具体痛点**：
1. 投出去的简历没人给反馈 —— 不知道岗位匹配度、优势短板、关键词缺口在哪；
2. 面试练习成本高 —— 找人对练难，练完也没有结构化复盘；
3. 面试录音一堆 —— 没有工具把它变成可检索、可对比的提升依据。

**产品闭环**：上传简历 → AI 结构化诊断 → 定制题/模拟面试 → 复盘评分 → 用 Agent 客服追问历史数据。

**为什么值得做成 Agent 项目**：全流程要跨「读用户私有数据（简历/面试/用量）」「调知识库」「调 LLM 生成」三类能力，天然需要工具调用 + 多步编排 —— 这也是把它包装成 Agent 岗项目经历的基础。

## 四、主要职责与贡献（痛点 → 方案 → 效果）

### 4.1 多模态输入解析（文档 + 语音）

- **痛点**：简历排版多样易解析失败；面试录音全靠回忆，无法量化复盘。
- **方案**：
  - 文档侧：PDF/docx 文本抽取 + 扩展名与 **magic bytes 双校验**（防改扩展名伪装）+ 文件名消毒 + `/api/**` 默认拒绝闸门；Celery 异步解析，提交即返回任务态（pending→processing→ready）。
  - 语音侧：**faster-whisper 本地转写**（不上传第三方 ASR，隐私可控；支持 base 快速档换速度）→ 转写文本**可人工编辑校正** → LLM **角色审核**（按面试官/候选人分段标注）→ 沿用模拟面试同一套**四维评分**报告口径。
- **效果**：语音面试记录从「不可复盘」变为可检索、可对比的结构化数据；音频上传在解码前即拦截伪装文件（415）。

### 4.2 双轨 Agent 编排（ReAct + StateGraph）

- **痛点**：单一 ReAct 轨适合「单轮问答 + 工具调用」，但跨多步长流程（读简历→补分析→匹配→出题→交付）缺少断点续跑与人工介入能力。
- **方案**：
  - **v1 ReAct 轨**：13 个工具 = 检索/查询类 9（知识库检索、我的简历、面试记录、问答原文、评分趋势、历史对话、用量统计、读分析报告、语料清单）+ 平台说明 1 + 工具内 LLM 类 3（岗位匹配 / 出题 / 回答点评，独立限额）。**每请求闭包工厂**创建工具，绑定本次 `db` 会话与归属者，从根上避免多请求串数据；无身份时**显式拒绝**而非返回空结果。SSE 事件协议 `meta → (action → observation)* → delta* → done`，工具调用过程落库（JSONB）前端可折叠回看。
  - **v2 图编排轨**：`StateGraph` 串联 `planner → load → analyzer? → matcher → questioner → verifier(回环≤2) → hitl_gate → deliver`；条件边**跳过已有有效分析**；`PostgresSaver` 断点持久化（Alembic 预建 schema，避免请求路径跑 `setup()` 造成 `CREATE INDEX CONCURRENTLY` 与流式事务互等死锁）；`interrupt` **人工审批卡**（TTL 30min，到点终止且可从失败节点续跑），approve/abort 用**条件更新乐观锁**防并发。
  - **双轨并存**：`agent_v2_enabled` 开关，v2 异常不影响 v1。
- **效果**：工具路由 top-1 **40/40 = 100%**；v2 端到端黄金任务 **11/11**（含审批通过/拒绝/超时、坏输出回环、检索降级、越权 404、限额 429）。工具描述用「什么时候用 / 什么时候**不**用」三段式写，易撞的工具互相点名排他（如 `resume_lookup` 原文 ↔ `analysis_read` 结论）—— 这是把命中率做到 100% 的关键。

### 4.3 RAG 混合检索优化

- **痛点**：纯向量检索对专有名词/缩写（如 `JVM`、`B+ 树`）不敏感，top1 常被「岗位 JD」类泛化文档挤占。
- **方案**：切块器段落合并（~600 字/块 + 60 字重叠，无内容丢失）→ 向量路走 pgvector HNSW（数据库内排序）+ 词法路 jieba 分词 + 手写 BM25 → **RRF 融合**；回答带可折叠引用来源；未命中时清空上一轮残留引用，避免编造「知识库说」。
- **效果**：49 题黄金问答集 **hit@1 71.4% → 87.8%**、**hit@5 91.8% → 100%**；报告落 `data/kb_eval/report.md`，改检索逻辑必须与基线对比。

### 4.4 面试官 Agent 智能追问（v4.5）

- **痛点**：候选人一句「差不多 / 就是这么做的」答完，面试按流程推进，练不到深度 —— 真人面试官会追问。
- **方案**：每轮作答后由评分节点产出 `depth_signal`，判定为 `weak`（或 ≤4 分）即触发追问节点，用面试官人设口吻生成「你刚才提到……能再展开吗」式追问并挂起等作答；**追问不占主问题轮次**、预算可配（`interview_max_follow_ups`，默认 1/问，0 即关闭）；与 checkpoint 闭环兼容，旧会话可续跑。
- **效果**：面试图评测场景 **6 → 8 全过**（含「弱回答触发追问」「预算归零直接进下一题」两条新场景）。

### 4.5 工程可信度（把「作品集」做成「能上线的系统」）

- **测试**：**414 个 pytest 全绿**（2026-10-11 实测），覆盖率 **90.3%**（CI 口径 `--cov=app`，门槛 85%；服务层口径 `--cov=app/services` 实测 89.83%）；全部 mock AI/embedding/whisper，跑测试不烧额度。
- **质量门禁**：CI 跑 ruff check + format、pytest 覆盖率门槛、pip-audit / npm audit 依赖审计（Dependabot 周检）；`release_check.py` 机器核对文档口径（测试数/工具数/迁移数/版本号），根治「文档写 401 实际 403」这类失真。
- **安全**：JWT HttpOnly Cookie + Argon2 密码哈希；简历/分析/面试全量按 `user_id` 隔离（跨用户 404）；简历软删除可审计；登录防爆破迁 Redis 集中计数且 Redis 故障 fail-open 不阻塞登录；日志不打印简历正文与 API Key。
- **依赖治理**：LangChain 0.3/LangGraph 0.2 整体升 1.x，v1 executor 重写为 `create_agent + astream_events` 桥（**SSE 协议零变化**），pip-audit 漏洞 **14 → 0**。

## 七、面试预案（高频追问 + 建议答法）

**Q1：为什么同时用 LangChain 和 LangGraph 两套？不是重复造轮子吗？**
> 两者解决不同形态的问题：单轮「问一句、调几个工具、回一句」用 ReAct 更轻；跨 5~6 步的长流程需要状态可视、断点续跑、人工介入，这是 StateGraph 的强项。双轨并行且用开关隔离，v2 出问题不影响 v1 —— 是**渐进式替换**，不是重复建设。

**Q2：多模态具体体现在哪？**
> 两条输入模态：**文档**（PDF/docx 解析 + 双校验 + hash 去重）和**语音**（faster-whisper 本地转写 → 说话人角色切分 → 四维评分）。**尚未做图像/视觉理解**（见 §八 边界说明），简历、面试录音是这个场景真正的多模态来源。

**Q3：RAG hit@5 做到 100% 会不会是评测集过拟合？**
> 评测集 49 题是人工构造的同域问题，语料也是同域八股文档，绝对分偏乐观 —— 这是已知局限。价值在于**同集对比**：纯向量 91.8% vs 混合 100%，8 道翻转题全是「专有名词被 JD 泛化文档挤占」的典型，说明 BM25 词法路补的正是向量路的短板，是机制性收益而非调参运气。

**Q4：13 个工具怎么保证 LLM 不选错？**
> 三条：① 工具描述按「什么时候用 / 什么时候不用」三段式写；② 易混工具**互相点名排他**（查简历原文 vs 读分析结论，描述里互相指认）；③ 40 题×13 工具做回归基线，改描述必须重跑对比。

**Q5：工具会不会查到别人的数据？**
> 工具是**每请求闭包工厂**创建的，创建时就把本次请求的 db 会话和归属者绑死，工具内部一律按归属者过滤；没有身份时返回明确拒绝而不是空结果（空结果会被 LLM 解释成「你确实没有」，是错的）。越权访问在 e2e 里有专门用例（他人 run 读与审批均 404）。

**Q6：PostgresSaver 踩过什么坑？**
> 最大一个是 `setup()` 建索引会跑 `CREATE INDEX CONCURRENTLY`，在流式事务里和 checkpoint 写入互等造成死锁 —— 解法是**用 Alembic 预建 schema**，请求路径不跑 `setup()`。另外升级 LangGraph 后旧 checkpoint 能读不能续跑，升级窗口要先清在途 run。

**Q7：覆盖率 90% 怎么做到的？为什么可信？**
> 测试全部 mock AI/embedding/whisper，不烧额度也不依赖外部服务，所以能在 CI 稳定复现；重点覆盖状态机分支（SSE 全分支、审批超时、回环重试、越权 sweep、限额 429）。另外 `release_check.py` 会机器核对文档口径与真实测试数一致，防止「文档写 401、实际 403」这类漂移。

**Q8：成本怎么控？**
> 每日限额双轨（匿名/user）+ 工具内 LLM 调用（出题/匹配/点评）独立限额 + 评测走离线确定性 stub（不烧额度）+ 国产模型 + 本地 embedding。

## 八、真实边界（别吹，会被问穿）

| 截图那版项目有 | 本项目实际 |

| 多模态**视觉**（dot.OCR、Qwen3-VL 图片理解） | ❌ **没有**。本项目多模态 = 文档 + 语音，不要写 OCR/VLM |
