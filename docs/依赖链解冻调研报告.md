## 1. 结论速览

1. **可以解冻**。1.x 全家桶（langchain 1.4.3 / langchain-core 1.6.6 / langgraph 1.2.12 / langgraph-checkpoint-postgres 3.1.2）在 Python 3.13.9 上 pip 解析一次通过、零冲突。
2. **推荐路径 A（整体切换）**：v1 与 v2 **必须同批**切到 1.x——实测 `pip install --dry-run "langgraph==1.2.12" "langchain==0.3.30"` 直接 `ResolutionImpossible`（langgraph 1.x 硬性要求 langchain-core>=1.4.7，与 langchain 0.3 要求的 core<0.4 互斥），不存在"只升 v2 留 v1"的中间态。
3. **工具层零改动**：`@tool` / `BaseTool` / 三段式 docstring 路由在 1.x 完全兼容（实测 invoke 通过），13 个工具与 `eval_agent_routing` 40/40 基线闸门原样保留。
4. **最大风险**：旧版（2.0.21）写下的 **interrupt 挂起 checkpoint 无法被新版（3.1.2）resume**——实测报 `TypeError: 'Interrupt' object is not subscriptable`。表结构本身兼容（同 4 张表、setup() 自动补迁移），能读不能续。升级窗口必须清场（作废/延时 waiting_approval 的在途审批）。
5. **v1 替代运行时已验证**：`langchain.agents.create_agent`（1.x 正主 API）配合现有 @tool 工具可完整跑通"工具调用 → 最终回答"闭环，`astream_events` 事件流含 `on_chat_model_stream`（token 级）/`on_tool_start`/`on_tool_end`，与 v1 现用 BaseCallbackHandler 的 SSE 事件一一对应。
6. **预估工作量：5–6 人日**（含升级窗口清场、v2/interview 图切换、v1 executor 重写、评测回归与文档收尾）。

### 2.2 依赖关系变化（✅实测 `pip show` / `importlib.metadata.requires`）

- `langgraph 1.2.12` 声明 `langchain-core>=1.4.7,<2` —— **0.2.76 时代 langgraph 不依赖 core，1.x 反向咬死 core**，这是混合版本不可行的根因。
- `langchain 1.4.3` 声明 `langgraph>=1.2.11,<1.3.0` —— langchain 1.x 的 agent 实现就是 langgraph 图，两包从此同进退。
- `langgraph-checkpoint-postgres 3.1.2` 只声明 `psycopg`（**不带 binary extra**）——纯 `psycopg` 在 Windows 缺 libpq 时 import 即挂（实验中亲测：`no pq wrapper available`，补装 `psycopg[binary]` 后正常）。**本项目 requirements.txt 本就写 `psycopg[binary]>=3.1`，保持即可，但要防止未来有人"精简"掉这个 extra。**
- 新增传递依赖：`xxhash`（langgraph）、`uuid-utils`/`langchain-protocol`/`orjson`（core/checkpoint 层），均纯 Python 或带轮子，无系统依赖（📄元数据推断，未逐个压测）。

### 2.3 混合版本可行性（✅实测）

```
pip install --dry-run "langgraph==1.2.12" "langchain==0.3.30" "langchain-openai<0.4"
→ ERROR: Cannot install langchain==0.3.30 and langgraph==1.2.12 ... ResolutionImpossible
```

**结论：v1/v2 只能整体切换或整体不动。**

## 3. 验证点实测记录

> 实验脚本位于临时目录（已随清理删除，关键脚本逻辑摘录见附录）。

### 3.1 `@tool` 装饰器与 `BaseTool`（工具层）——✅ 兼容

- `from langchain_core.tools import tool, BaseTool` 导入正常。
- 仿项目三段式 docstring 的 `@tool kb_search(query: str, top_k: int = 3)`：`.name` / `.description` / `.args` 属性齐全，`invoke({"query": ..., "top_k": 5})` 返回正确。
- `BaseTool` 子类（内嵌 `args_schema: type = ResumeLookupInput` 的项目写法）：实例化、`invoke` 均通过。
- **对照影响**：`backend/app/services/agent/tools.py` 全文零改动。

### 3.2 langchain_core 其余导入点——✅ 全存活

| 项目用法 | 1.x 实测 |
|---|---|
| `langchain_core.callbacks.BaseCallbackHandler`（v1 SSE 流式） | ✅ 可导入、可子类化，on_llm_new_token/on_tool_start/on_tool_end 签名可覆写 |
| `langchain_core.messages` AIMessage/BaseMessage/HumanMessage | ✅ |
| `langchain_core.prompts` ChatPromptTemplate/MessagesPlaceholder | ✅（仍存在；但新 agent API 不再吃 prompt 模板，见 3.4） |
| `langchain_core.language_models.BaseChatModel` | ✅ |

### 3.3 `langchain.agents` 旧 API——❌ 确认移除

```
from langchain.agents import AgentExecutor, create_openai_tools_agent
→ ImportError: cannot import name 'AgentExecutor' from 'langchain.agents'
```

1.x 的 `langchain.agents` 公开符号实测为：`AgentState, create_agent, factory, middleware, structured_output`。v1 的 `executor.py` 受直接影响（预期内，AGENTS.md 已有记录）。

### 3.4 v1 替代运行时与流式等价能力——✅ 跑通（路径 A 的核心依据）

用**脚本假模型**（不联网：第 1 轮吐 `tool_calls`，第 2 轮逐字吐最终回答）分别驱动：

1. **`langgraph.prebuilt.create_react_agent`**（✅ 仍可用但已标弃用）：`LangGraphDeprecatedSinceV10: create_react_agent has been moved to langchain.agents. Please update your import to from langchain.agents import create_agent. Deprecated in LangGraph V1.0 to be removed in V2.0.`
2. **`langchain.agents.create_agent`**（1.x 正主，✅ 推荐）：签名 `create_agent(model, tools=None, *, system_prompt=None, middleware=...)`。工具闭环：4 条消息（Human → AIMessage(tool_calls) → ToolMessage → 最终 AIMessage）完整走通，**prompt 模板被 `system_prompt` 参数取代**。

**流式事件对齐（v1 SSE 桥接可行性）**——`astream_events(version="v2")` 实测事件计数：

```
{'on_chain_start': 4, 'on_chat_model_start': 2, 'on_chat_model_stream': 23,
 'on_chat_model_end': 2, 'on_chain_stream': 6, 'on_chain_end': 4,
 'on_tool_start': 1, 'on_tool_end': 1}
```

- `on_chat_model_stream` 逐 token 吐 AIMessageChunk，拼回文本与最终回答**逐字一致**——等价 v1 的 `on_llm_new_token`；
- `on_tool_start` / `on_tool_end` 与 v1 回调事件同名同义，v1 的 action/observation SSE 事件可低成本桥接；
- 另测 `graph.stream(stream_mode="messages")`：直接产出 `(AIMessageChunk/ToolMessage, metadata)` 元组流，是更轻的替代桥。

### 3.5 PostgresSaver + checkpoint 迁移——⚠️ 读通续不通（本次最重要的实测）

一次性库 `ai_spiketest` 上三步实测：

| 步骤 | 结果 |
|---|---|
| ① 旧版（repo venv：langgraph 0.2.76 + checkpoint-postgres 2.0.21）建表跑图，interrupt 挂起落 checkpoint | ✅ 表 4 张：`checkpoints / checkpoint_blobs / checkpoint_writes / checkpoint_migrations`；`state.next=('gate',)` |
| ② 新版（spike venv：1.2.12 + 3.1.2）**不 setup** 直接读旧 checkpoint | ✅ `get_tuple` 找到、`graph.get_state().next` 正确返回 `('gate',)` |
| ③ 新版直接 `Command(resume=...)` 续跑旧挂起 | ❌ **`TypeError: 'Interrupt' object is not subscriptable`**（langgraph/pregel/_loop.py `_first → _pending_interrupts`） |
| ④ 新版对旧库 `setup()` | ✅ 幂等完成，migrations 补齐到 v0–v9，仍为同 4 张表 |
| ⑤ 新版全新 thread 完整周期：invoke → interrupt → Command(resume) → 跑完 | ✅ 最终状态 `steps=['loaded', "gate:{'decision': 'approved'}"]`，`next=()` |

**结论**：表结构/迁移机制兼容（新库 setup 即可），但**旧版序列化的 interrupt 挂起载荷新版解不开**——能读快照、不能续跑。升级前必须清场在途 run。

### 3.6 1.x 行为变化点（✅实测发现的差异）

- `graph.invoke()` 挂起返回值新增 `'__interrupt__': [Interrupt(...)]` 键（0.2.76 时代无）。**对本项目影响低**：`agent_v2/graph.py`（L645-646）与 `interview_graph/graph.py`（L423-424）判定挂起均走 `graph.get_state(config).next`，实测该方法 1.x 可用且语义不变；两处均不读 invoke 返回值里的 interrupt 信息。
- `langgraph-checkpoint` 4.x serde 出 `LangChainPendingDeprecationWarning: allowed_objects 将来默认值会变`（旧 venv 0.2.x 侧打印）——观察项，非阻塞。

### 3.7 其它

- `ChatOpenAI(model=..., api_key=..., base_url=..., streaming=True)` 在 langchain-openai 1.6.7 下构造成功（✅；真实请求未发，⚠️未验证）。
- Python 3.13.9 上全部实验跑通，各包 requires-python >=3.10（✅）。

## 5. 推荐迁移路径

### 5.1 方案对比

| | 方案 A：整体切 1.x（v1 用 create_agent） | 方案 B：v1 改 openai-sdk 裸写 while 循环 |
|---|---|---|
| v2/interview 图 | 切 langgraph 1.x（导入点已验证兼容） | 同左（B 只替代 v1） |
| v1 运行时 | `langchain.agents.create_agent` + `astream_events` 桥 SSE | 手写：13 个工具的 JSON Schema、tool_calls while 循环、流式增量、错误重试、用量统计 |
| 工作量 | **5–6 人日** | 6–9 人日（📄推断：无生态兜底，工具协议手写量与双份维护成本高） |
| 风险 | 集中在 R6（清场）与 R10（参数语义） | 路由质量回归、双实现漂移；失去 eval_agent_routing 的直接可比性 |
| 结论 | **推荐** | 不推荐（仅在决定彻底去 langchain 依赖时再议） |

### 5.2 分阶段实施（方案 A）

**铁律：整个迁移期 `tools.py` 与评测基线不动。**

- **P0 升级窗口清场（0.5 人日）**
  发布步骤固化：停写 → 处理 waiting_approval 审批单（作废或延时，error 文案指向"升级后重新发起"）→ 进行中图会话（interview wait_answer）同样处理 → 复用 v4.0.1 lifespan 孤儿 run 回收逻辑兜底 planning/running。langgraph_* 表**不迁移数据**（历史快照只读兼容）。

- **P1 v2 + interview 图切 langgraph 1.x（2 人日）**
  改动面（实测导入全兼容，预期接近纯版本号变更）：
  - `backend/requirements.txt` / `requirements.lock`：langchain 1.4.x、langchain-core 1.6.x、langchain-openai 1.6.x、langgraph 1.2.x、langgraph-checkpoint-postgres 3.1.x，保持 `psycopg[binary]`；
  - 代码：两个 graph 文件按需微调（预期仅 `__interrupt__` 无关、无需改）；新增一次 `PostgresSaver.setup()` 习惯确认（新空库首次启动建表）；
  - 回归：pytest 363 全绿 → `eval_agent_e2e` 11/11 → `eval_interview_graph` 6 场景 → 真机冒烟 v2 审批流与面试图断点续跑。

- **P2 v1 executor 重写（2–3 人日）**
  - `executor.py`：`AgentExecutor` 组装改为 `create_agent(llm, tools, system_prompt=系统段)`；prompt 模板的其余段落并入 system_prompt；
  - SSE 桥：后台线程 + `_QueueCallback` 改为消费 `astream_events`（或线程内跑 `stream(stream_mode="messages")`），事件映射 `on_chat_model_stream→token`、`on_tool_start/on_tool_end→action/observation`，保持现有事件总线与前端协议不变；
  - `max_iterations` → `recursion_limit`；`return_intermediate_steps` 若有消费点改从事件流取；
  - 真机冒烟（DeepSeek）：13 工具逐类抽测 + `eval_agent_routing` 对比 40/40 基线（工具与 docstring 未动，预期持平；若有漂移优先查模型侧 tool-calling 协议差异而非改 docstring）。

- **P3 收尾（0.5 人日）**
  requirements.lock 重生成、AGENTS.md/README 版本口径与"三条实战教训"沉淀、CI 全绿、（若涉及）tag。

### 5.3 明确不动清单

- `app/services/agent/tools.py`（13 工具全部，含 docstring 路由文案）
- 评测资产：`data/agent_eval/`、`data/kb_eval/` 黄金集与基线数字（作为回归闸门，不是迁移对象）
- kb/RAG 全链路（jieba/BM25/pgvector，与 langchain 无关）
- 前端、事件总线协议（action/observation/token 事件名不变）
- `app/core/ai_client.py` 代码（仅随 openai SDK 3.x 回归验证）
