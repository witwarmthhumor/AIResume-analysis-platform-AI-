# AI 简历分析 + AI 模拟面试 — 后续开发规划

> **本文件是干嘛的**：v3.4 之后的方向路线图——哪些方向要做、为什么这个顺序、每个方向怎么算做完。
> 定位基线：**个人学习 + 求职作品集**（清晰的 Git 历史与可打开的线上地址本身就是展示内容）。
> 建立日期：2026-09-14 · 起点版本：v3.4（main @ d5ce624，tag v3.4）
> 权威需求仍以 [PROJECT-PLAN.md](../PROJECT-PLAN.md) 为准；本文件只负责「v1.0 封版之后」的规划。

---

## 0. 一句话结论

**功能开发已完结（v0.1→v3.4 共 12 个版本），短板全部集中在「让别人看到」和「让它随时能跑」这两件事上。**
因此后续前两批不做新功能，只做：**可演示性闭环 + AI 通道高可用 + 工程质量基线 + 文档收口**；新功能（Agent 多工具、RAG 提优、面试复盘可视化）放在第三批。

## 4. 各方向详情

### 方向 A · 可演示性闭环（P0）

**预期目标**：把 URL 发给任何人，30 秒内能跑通「上传简历 → 出分析报告 → 面一场 → 问一次 AI 客服」。

| 任务 | 内容 | 验收标准 |
|---|---|---|
| A1 线上部署复核 | 云服务器跑 `docker compose -f docker-compose.prod.yml up -d`；只开 80/443；HTTPS 后置 `JWT_SECURE_COOKIE=true` | 手机流量访问域名，`/health/ready` 全绿 |
| A2 演示账号与种子数据 | 固定演示账号 + 预置 1 份简历、1 场面试、预置语料；密码只写进部署环境变量，不入 Git | 登录演示账号即见完整历史，无需现传文件 |
| A3 README 演示入口 | 顶部加「在线演示」地址 + 3 张关键界面截图（登录/报告/面试） | README 首屏 3 行内看到地址 |
| A4 冷启动优化 | prod 首次启动预拉 nomic-embed-text；说明首次启动耗时 | 全新机器到可用 ≤ 5 分钟 |

**风险**：公网暴露简历上传入口 → 必须有每日限额（已有 `usage_logs` 限流）+ 演示账号只读降级开关。

---

### 方向 B · AI 通道高可用（P0）

**预期目标**：不再被单一账户余额卡死；换模型只改 `.env` 三行（这是 PROJECT-PLAN §3 早已承诺的能力，需实测兑现）。

| 任务 | 内容 | 验收标准 |
|---|---|---|
| B1 多 provider 实测 | DeepSeek ↔ 通义 / Kimi 至少两路互切；`AI_BASE_URL` / `AI_MODEL` / `AI_API_KEY` 三行完成 | 切到第二家后分析+面试+客服三条链路均通 |
| B2 失败分级话术 | 402 余额 / 429 限流 / 超时 / 非法 JSON 四类分别给用户可读提示与恢复时间 | 拔掉 Key 后页面不白屏，提示可读 |
| B3 本地 LLM 演示模式 | `DEMO_MODE=true` 时 LLM 走本地 Ollama（零成本、断网可跑） | 断网仍能演示完整流程（质量可降级） |
| B4 AI 可达性自检 | `/health/ready` 增加 AI 通道探测（可开关，避免拖慢） | 巡检一眼看出是"应用挂了"还是"余额没了" |

**建议**：B1 与 B3 一起做——它们是同一套封装层的两种输出，改动集中在 `services/ai_client.py` 与 `services/agent/llm_factory.py`。

---

### 方向 C · 工程质量基线（P1）

**预期目标**：README 上挂一排绿色徽章，且徽章是真的。

| 任务 | 内容 | 验收标准 |
|---|---|---|
| C1 GitHub Actions CI | `ruff check` + `pytest`（services 起 pgvector/pg16 + redis）+ `npm run build` | PR/推送自动跑，徽章绿 |
| C2 覆盖率门槛 | 引入 `pytest-cov`，先记录基线再设门槛（建议服务层 ≥70%，不设全局虚高值） | CI 输出覆盖率，低于门槛失败 |
| C3 格式与钩子收口 | 一次性 `ruff format .` 收掉 18 文件漂移；加 `.pre-commit-config.yaml` | `ruff format --check` 全绿 |
| C4 依赖锁定 | `requirements.txt` 补 `pip-compile` 或生成 `requirements.lock`；清掉 `httpx2` | 新机器 `pip install -r` 装出的版本与开发机一致 |

**顺序建议**：C3 → C1 → C2 → C4（先让格式绿，CI 才不会第一天就红）。

### 方向 E · AI 能力深化（P2，亮点方向）

| 任务 | 内容 | 量化验收 |
|---|---|---|
| E1 Agent 多工具 ReAct | 在 `kb_search` 之外增加 `resume_lookup`（本人简历检索）、`interview_history`（历史面试表现）、`usage_stats`（我的用量）三个工具 | 一次提问可触发 ≥2 个工具，`tool_steps` 在前端可见 |
| E2 RAG 检索提优 | 混合检索（BM25/jieba + 向量 RRF 融合）或 rerank，目标把 3 题结构性未命中（聚簇索引/乐观锁/动态规划）救回来 | `scripts/eval_rag.py` 对比基线：hit@1 73.5% → **≥85%**，hit@5 ≥95% |

## 5. 推进顺序（三批）

| 批次 | 主题 | 任务组合 | 完成信号 |
|---|---|---|---|
| **第 1 批** | 解锁演示（最小成本、最高回报） | D4 → B1+B3 → A1+A2 → A3 | 拿到可外发的公网 URL + 演示账号 |
| **第 2 批** | 工程可信度 | C3 → C1 → C2 → C4 → D1~D3、D5 | README 有绿徽章，文档与代码同版本 |
| **第 3 批** | 能力深化 | E2 → E1 → E3 → E4 | RAG 指标写进 README，Agent 演示多工具 |
| **远期** | 按需 | F 组 | —— |

**为什么是这个顺序**

1. **先修交付面**：作品集的全部价值在"别人能看到"，功能再多打不开也白搭；第 1 批全部是低频改动 + 高确定性。
2. **再补可信度**：CI 与覆盖率让"110 个测试全绿"从口头变成可验证，是第 2 批最划算的投入。
3. **最后做亮点**：新功能最容易烂尾，且此前已出现过"文档先行、实现滞后"的情况——放在前两批之后，地基稳了再上。
4. **每批结束打 tag**：第 1 批 → `v3.5`，第 2 批 → `v3.6`，第 3 批 → `v3.7`；每个 tag 都推 GitHub 并写进 README 版本表。

## 6. 执行纪律（沿用既有铁律）

1. **一次只推一个方向**，做完一个方向再开下一个，禁止并行铺开。
2. 改提示词 → 递增 `PROMPT_VERSION`，并用 `test-resumes/` 5 份跑回归对比。
3. 改切块 / embedding / 检索 → 必跑 `scripts/eval_rag.py` 并对比 `data/kb_eval/report.md` 基线。
4. 改模型结构 → 必走 Alembic 迁移，禁改表。
5. CI 上线后：**CI 不绿不合并**。
6. 单方向实际耗时超预估 1.5 倍 → 砍范围（沿用 PROJECT-PLAN §8 裁剪规则），不顺延。

## 7. 明确不做（防烂尾）

- 不引入 LangGraph / LangChain 1.x（AgentExecutor 已满足需求，升级 = 重写）
- 不做支付 / 配额计费 / 多租户后台
- 不做移动端 App、不做国际化
- 不为了"技术新颖"替换已稳定的技术栈（pgvector / Ollama / Vue3 均保留）
