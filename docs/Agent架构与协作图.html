一、分层架构：Agent 在整体架构中的位置

Agent 只占第 3 层——向上被 API 路由驱动，向下把「怎么做」交给共享能力层；所有 LLM 调用最终收敛到 ai_client 一处。

▼ 经 Vite 代理 / Nginx，/api/** 全部经 ASGI 登录闸门（auth_gate）
② API 层backend/app/api/*
POST /api/agent/ask（SSE） /api/agent-v2/*（run/stream/approve） /api/interviews/* /api/analyses /api/question-banks
▼ 路由只做装配与限流，不做业务编排
③ Agent 编排层本图主角 · 决定「何时调什么」

▼ v1 三工具 + v2 三节点收敛到能力层；面试图例外：直调 ai_client（见三·注③）

二、三类 Agent：类型与职责

判据：有「自主决策 + 工具/流程循环」的才算 Agent；单次 LLM 调用链不算（见底部边界澄清）。

v1 · AI 客服 对话式 ReAct
职责即时问答与个人数据查询：13 个工具覆盖知识库检索、简历 / 面试记录 / 分数趋势 / 用量读取、JD 匹配、出题、回答点评
运行特征单会话内多步工具循环（≤6 次迭代）；SSE 流式（action / observation / delta）；会话 session_type='agent' 与在线对话隔离
治理主循环 30 次/日 · 工具内 AI 20 次/日 · 路由评测 40/40
落点services/agent/executor.py
v2 · 一键求职准备 编排式 + HITL
职责长任务编排：读简历 → AI 分析 → 岗位匹配 → 模拟出题 → 人工审批后创建面试场
运行特征verifier 回环（每节点 ≤2 次）· interrupt 审批（TTL 30 分钟）· PostgresSaver 断点续跑 · 单 run token 熔断 30000
治理agent_v2_enabled（关 → 全部 503 回 v1）· 10 run/日 · e2e 评测 11/11
落点services/agent_v2/graph.py
面试图 · S1 流程状态机
职责驱动整场模拟面试：出题（题库优先、题尽才调模型）→ 评分 → 生成最终报告
运行特征wait_answer 纯 interrupt 零副作用 · checkpoint 存独立 langgraph schema · 每轮 trace 从 session.trace_json 续接
治理interview_graph_enabled（无 checkpoint 自动回退 legacy 单轮）· token 记 interview_message · 6 场景评测
落点services/interview_graph/graph.py
边界澄清——不算 Agent 的 AI 链路：① 简历分析 analyze_resume：单次结构化 LLM 调用（同步执行），被 v2 analyzer 节点复用；② 题库生成 question_bank_service：独立 chat_json 链路，与两套 Agent 无关；③ 录音点评 / 转写：service 直调。共同点：无工具循环、无图编排、无自主决策。

三、调用与协作关系：谁调用谁

同一能力只实现一次：v1 工具与 v2 节点从上向下收敛到能力层；跨 Agent 之间没有函数调用，只有数据交接与开关隔离。

v1 AI 客服发出 经 ReAct 循环选择工具
kb_search 工具→kb_retrieve（混合检索）
job_match 工具→run_job_match
question_gen 工具→run_question_generation
answer_review 工具→run_tool_llm（限额+记账）+chat_json
interview_history / score_trend / interview_transcript→只读面试数据表（SQL，无函数调用）
v2 图节点发出 按 state 确定性流转
load_resume 节点→find_latest_resume
analyzer 节点→ai_client.analyze_resume（复用简历分析能力）
matcher 节点→run_job_match
questioner 节点→run_question_generation（内含 kb_retrieve）
deliver 节点→interview_service.create_session（审批通过后建面试场，仅写数据 · 注①）
面试图节点发出 绕过能力层
ask_question→chat_json（题库有题先查题库，零 LLM）
score_answer→chat_json
generate_report→chat_json
三节点直调 ai_client：不经能力层、不受工具内 20 次/日限额；token 由 API 层记 interview_message 账（注③）

共享能力层 agent_capabilities（v1 工具与 v2 节点收敛于此）

kb_retrieve run_job_match run_question_generation find_latest_resume run_tool_llm（限额→执行→记账）

底座：ai_client（全项目唯一 LLM 封装）与 kb_service（混合检索）

ai_client.chat_json / analyze_resume / stream_chat → DeepSeek kb_service.search_chunks →（kb_hybrid_enabled）→ 向量 + BM25 RRF → pgvector / Ollama 例外：v1 主循环走 llm_factory（LangChain ChatOpenAI），读同一份 settings
注① v2 → 面试体系是数据交接、不是运行时交接：approve 后 resume 图继续跑，deliver 节点仅调用 create_session 写入会话行 + 开场白（不建 checkpoint）；用户随后进入该会话答题时因无 checkpoint 走 legacy 单轮路径，只有显式「开始模拟面试」新建的会话才由面试图接管。
注② v1 与 v2 / 面试图零函数调用：v1 executor 不 import agent_v2 与 interview_graph；客服读面试记录是对 InterviewSession / InterviewMessage 的只读查询。故障域靠开关隔离（agent_v2_enabled 关闭 → v2 接口 503，客服照常）。
注③ 面试图不走能力层：三个 LLM 节点直调 ai_client.chat_json，因此不受工具内每日限额约束，token 按 interview_message 口径在 API 层记账——这是刻意设计：面试是主产品流程，不应被客服工具限额「腰斩」。
注④ LLM 双构造路径、同一配置：全项目收敛 ai_client（OpenAI SDK），唯一例外是 v1 主循环用 llm_factory 构造 LangChain ChatOpenAI（需要 streaming 回调），base_url / key / model 读同一份 settings。
