# 数据库与 SQL 面试题

## 什么是数据库索引，聚簇索引与非聚簇索引的区别

索引是帮助数据库高效定位数据的结构，类似书的目录。MySQL InnoDB 使用 B+ 树实现索引。聚簇索引（Clustered Index）的叶子节点直接存整行数据，一张表只能有一个聚簇索引，默认主键就是聚簇索引。非聚簇索引（Secondary Index）的叶子节点存主键值，查询时先走二级索引找到主键，再回表查完整数据，这个过程叫回表查询。如果查询所需的列都包含在二级索引中（覆盖索引），则无需回表，性能更好。聚簇索引按主键顺序存储数据，物理上连续。

## 最左前缀原则是什么

MySQL 联合索引遵循最左前缀原则：查询条件必须从索引的最左列开始匹配，索引才能生效。例如索引 (a, b, c)，查询条件 WHERE a=1 AND b=2 会走索引，WHERE b=2 不会走索引（跳过了 a），WHERE a=1 AND c=3 只会走 a 这一列（b 被跳过）。设计联合索引时，把区分度高的列放左边，经常作为等值查询的列放左边，范围查询的列放最后。可以利用这个原则，用较少的联合索引覆盖更多的查询模式，减少索引数量。

## 什么是 SQL 注入，如何防范

SQL 注入是攻击者通过拼接 SQL 字符串，把恶意 SQL 代码作为输入传入，导致数据库被攻击。例如用户输入 ' OR '1'='1 使 WHERE 条件永远为真。防范方法：1) 使用参数化查询（PreparedStatement、ORM 框架的参数绑定），不让用户输入拼接到 SQL 字符串中，这是最根本的防御；2) 对用户输入进行白名单校验（特别是排序字段、表名等无法参数化的位置）；3) 最小权限原则：应用层数据库账号只给 CRUD 权限，不给 DDL 权限；4) 使用 ORM 框架（MyBatis 用 #{} 而不是 ${}，JPA 自动参数化）。

## 什么是数据库事务的 ACID

ACID 是数据库事务的四个特性：原子性（Atomicity）：事务中的所有操作要么全部成功提交，要么全部失败回滚，不会部分执行。一致性（Consistency）：事务执行前后数据库都处于一致状态，约束不破坏。隔离性（Isolation）：并发事务之间互相隔离，一个事务的执行不应该被其他事务干扰。持久性（Durability）：已提交的事务对数据的修改是永久的，即使系统崩溃也不会丢失。MySQL InnoDB 通过 undo log 保证原子性（回滚）、redo log 保证持久性（崩溃恢复）、锁和 MVCC 保证隔离性，开发者通过约束和业务逻辑保证一致性。

## 为什么要分库分表，分库分表有哪些策略

分库分表解决单库单表数据量过大导致的性能问题。单表数据达到千万级后，B+ 树高度增加，索引维护成本上升，写入瓶颈凸显。分库：按业务拆分到不同数据库（如用户库、订单库），降低单库压力。分表：按某个维度把一张表拆成多张物理表，常见策略：水平分表（按取模、范围、哈希），垂直分表（把大字段拆分到扩展表）。分片键的选择至关重要，ID 取模简单但扩缩容难，一致性哈希扩缩容影响小，业务 ID 分片天然友好。分库分表后带来的问题：跨节点查询（排序、聚合、分页）、分布式事务、全局唯一 ID，需要中间件（ShardingSphere、MyCAT）或应用层处理。

## 如何优化大分页查询

传统分页 SELECT * FROM table LIMIT 100000, 20 会扫描 100020 行后丢弃前 100000 行，效率极低。优化方案：1) 子查询延迟关联：先查主键再用主键关联查数据，SELECT * FROM table t JOIN (SELECT id FROM table ORDER BY id LIMIT 100000, 20) tmp ON t.id=tmp.id；2) 游标分页（推荐）：基于排序条件的游标，WHERE id > last_id ORDER BY id LIMIT 20，无需扫描已跳过的行，适合无限滚动场景；3) 覆盖索引：查询列都在索引中，避免回表。游标分页是性能最好的方案，但不支持跳页，适合瀑布流场景。

## MySQL 的日志体系

MySQL 的三种核心日志：binlog（二进制日志，Server 层，记录逻辑变更，用于主从复制和 PITR 数据恢复）、redo log（重做日志，InnoDB 存储引擎层，记录物理页修改，保证事务持久性，WAL 预写日志机制，崩溃恢复时回放）、undo log（回滚日志，记录数据修改前的版本，用于事务回滚和 MVCC 快照读）。写入顺序：事务提交时先写 redo log（prepare 状态）→ 写 binlog → 提交事务（redo log 设为 commit 状态），这个两阶段提交保证 binlog 和 redo log 一致，崩溃恢复时根据两阶段状态决定是提交还是回滚。redo log 是循环写，binlog 是追加写。

## 什么是数据库的乐观锁和悲观锁

悲观锁（Pessimistic Locking）认为并发冲突大概率发生，操作前先加锁，防止其他事务修改。MySQL 实现：SELECT ... FOR UPDATE，事务结束时释放。优点是安全，缺点是并发度低，容易死锁。乐观锁（Optimistic Locking）认为冲突小概率发生，操作时不加锁，提交时验证是否冲突。实现方式：版本号（version）或时间戳，UPDATE table SET count=count-1, version=version+1 WHERE id=? AND version=old_version。如果影响行数为 0 说明冲突，重试或报错。优点是并发度高，适合读多写少的场景。悲观锁适合写操作频繁、冲突发生率高的场景，乐观锁适合读多写少的场景。

## 如何设计数据库表来存储树形结构

树形结构的常见存储方案：1) 邻接表（Adjacency List）：每行存 parent_id，查询简单，但递归查询需要 CTE（WITH RECURSIVE），MySQL 8.0 支持；2) 路径枚举（Path Enumeration）：每行存从根到当前节点的路径字符串，类似 "/1/2/3/"，查询子节点用 LIKE，但路径长度有限、维护麻烦；3) 嵌套集（Nested Set）：每行存 left 和 right 值，查询子树高效，但增删改复杂；4) 闭包表（Closure Table）：用单独的表存所有祖先-后代关系，查询灵活，写入复杂，存量大。实际项目最常用的是邻接表 + CTE，简单够用，MySQL 8.0 以上支持递归查询。如果树结构频繁写且层级深，考虑闭包表。

## 什么是数据库的范式与反范式

范式是数据库设计的一组规范，减少数据冗余：第一范式 1NF（列不可再分，原子性），第二范式 2NF（满足 1NF，非主键列完全依赖主键，消除部分依赖），第三范式 3NF（满足 2NF，非主键列直接依赖主键，消除传递依赖，不依赖其他非主键列），BCNF（更严格，主键内部也不存在部分依赖）。反范式是为了性能牺牲部分规范性，通过冗余字段减少多表关联查询。实际项目通常做到 3NF，然后针对高频查询做反范式优化（冗余字段、汇总表、缓存字段）。比如订单表冗余用户姓名和地址，避免每次查询都 JOIN 用户表。范式保证数据一致性，反范式提升查询性能，需要在两者之间找平衡。

## 什么是数据库的 EXPLAIN，怎么看

EXPLAIN 是 MySQL 分析查询执行计划的关键命令。EXPLAIN SELECT ... 的输出主要字段：type（访问类型，从好到差：system > const > eq_ref > ref > range > index > ALL），key（实际使用的索引），rows（预估扫描行数），Extra（额外信息，Using index 覆盖索引、Using filesort 需要额外排序、Using temporary 用了临时表）。type 为 ALL 是全表扫描，需要优化。rows 远大于实际结果数说明选择性差。Extra 出现 Using filesort 或 Using temporary 通常需要加索引或优化 SQL。EXPLAIN 的预估行数只是估计值，实际执行可能不同，但足以判断索引是否生效。

## 如何理解数据库的读写分离

读写分离把数据库的读操作和写操作分散到不同的实例上，主库（Master）处理写入，从库（Slave）通过主从同步复制数据后处理查询。目的：1) 读扩展，增加从库节点提升查询吞吐；2) 主库专注写入，避免查询拖慢写入；3) 高可用，主库故障可将从库提升为主库。实现方式：应用层配置多数据源（Spring 的 AbstractRoutingDataSource）、中间件代理（MyCat、ShardingSphere）、云数据库自带读写分离地址。注意：主从同步有延迟，刚写入的数据可能查不到，需要根据业务容忍度决定是否强制读主库。写操作后立即读的场景走主库，无实时性要求的读走从库。
