# 网络与操作系统面试题

## TCP 的三次握手为什么是三次

三次握手建立 TCP 连接：客户端发送 SYN（seq=x），服务端回复 SYN+ACK（seq=y, ack=x+1），客户端再发送 ACK（ack=y+1）。为什么是三次而不是两次：两次握手无法防止失效的连接请求报文突然到达服务端。比如客户端发送的连接请求在网络中滞留，客户端超时重传后建立连接、正常通信、释放连接，此时滞留的旧请求才到达服务端，两次握手会让服务端误以为客户端要建立新连接而分配资源等待，浪费服务端资源。三次握手让服务端收到 ACK 才进入 ESTABLISHED，能确认客户端具备收发能力。四次则多余，因为服务端的 SYN 和 ACK 可以合并为一个报文。

## TCP 四次挥手为什么需要 TIME_WAIT

TCP 断开连接需四次挥手：主动方发 FIN → 被动方回 ACK → 被动方发 FIN → 主动方回 ACK。主动方最后回 ACK 后进入 TIME_WAIT 状态，等待 2MSL（最大报文段生存时间，约 1~4 分钟）才关闭。TIME_WAIT 有两个原因：1) 保证最后一个 ACK 能到达被动方：如果 ACK 丢失，被动方会超时重发 FIN，主动方需要留够时间处理重发的 FIN；2) 让本连接中所有旧报文在网络中消失：防止滞留在网络中的旧连接报文（序列号可能相同）干扰新连接。大量短连接（如高并发 HTTP 请求）会产生大量 TIME_WAIT 连接，可以通过开启 tcp_tw_reuse（复用 TIME_WAIT 连接，前提是开启 tcp_timestamps）来缓解，但不能滥用。

## 简述 TCP 的拥塞控制

拥塞控制是 TCP 根据网络状况动态调整发送速率，避免网络过载。四个算法：1) 慢启动（Slow Start）：连接建立后拥塞窗口 cwnd 从 1 开始，每收到一个 ACK 指数增长（1、2、4、8...），直到达到慢启动阈值 ssthresh。2) 拥塞避免（Congestion Avoidance）：超过 ssthresh 后 cwnd 线性增长，每次 RTT 加 1，试探网络容量。3) 快重传（Fast Retransmit）：收到 3 个重复 ACK 就立即重传丢失报文，不必等超时。4) 快恢复（Fast Recovery）：快重传后 cwnd 减半进入拥塞避免（或新算法直接调整），而不是回到慢启动。发送速率 = min(拥塞窗口 cwnd，接收窗口 rwnd)。TCP 拥塞控制的本质是"加性增、乘性减"，在网络拥塞时快速降低速率。

## 进程与线程的区别

进程是操作系统资源分配的基本单位，拥有独立的地址空间（代码、数据、堆栈）、文件描述符等资源；线程是 CPU 调度的基本单位，是进程内的执行流，同一进程的线程共享地址空间和资源。区别：1) 资源：进程拥有独立资源，线程共享所属进程的资源；2) 开销：进程创建/切换开销大（需要分配和回收资源、切换地址空间），线程切换开销小（只切换上下文，不切换地址空间）；3) 通信：进程间通信需要 IPC（管道、消息队列、共享内存、Socket），线程间通过共享变量通信但需要同步（锁、信号量）；4) 崩溃影响：进程间互不影响，一个线程崩溃（如段错误）可能导致整个进程崩溃。多进程适合稳定性要求高、需要隔离的场景，多线程适合计算密集且需要共享数据的场景。

## 进程间通信 IPC 有哪些方式

进程间通信（IPC）方式：1) 管道（Pipe）：匿名管道用于父子进程，命名管道（FIFO）可用于任意进程，单向字节流。2) 信号（Signal）：异步通知，如 SIGTERM、SIGKILL，只能传简单信号不能传大量数据。3) 消息队列（Message Queue）：内核维护的消息链表，按类型读取，有消息边界。4) 共享内存（Shared Memory）：多个进程映射同一块物理内存，速度最快（不经过内核拷贝），但要自己处理同步（配合信号量）。5) 信号量（Semaphore）：用于进程间同步和互斥，不是数据传输。6) Socket：可用于本机或跨网络进程通信，最通用。选型：要求高性能大流量用共享内存+信号量；要求简单可靠、数据量小用消息队列或管道；跨机器用 Socket。Python 的 multiprocessing 底层用管道实现，Redis 等常用网络协议走 Socket。

## 什么是用户态和内核态

CPU 指令分为特权指令和非特权指令。内核态（Kernel Mode）：可以执行所有指令，包括访问硬件、修改内存映射等特权操作。用户态（User Mode）：只能执行非特权指令，不能直接访问硬件和内核数据结构。系统调用（syscall）是用户态请求内核态服务的唯一入口：当应用程序需要读文件、创建进程、收发网络包时，通过系统调用陷入内核执行，完成后返回用户态。为什么要区分：保护系统安全，防止用户程序误操作或恶意破坏系统（如直接格式化硬盘）。频繁的系统调用（如大量小文件 IO）会成为性能瓶颈，因为每次都要切换上下文（保存用户态寄存器、加载内核态），所以有零拷贝（sendfile、mmap）、批量系统调用（io_uring）等优化。上下文切换的成本远高于普通函数调用。

## 操作系统的虚拟内存

虚拟内存让每个进程拥有独立的、连续的虚拟地址空间（如 64 位系统每个进程 128TB 虚拟空间），通过页表映射到物理内存。好处：1) 进程隔离：进程间虚拟地址互不可见，一个进程不能访问另一个进程的内存。2) 内存抽象：程序可以访问比物理内存更大的地址空间，不用的页换出到磁盘（swap）。3) 内存保护：页表项有权限位（读、写、执行），防止越权访问。4) 共享内存：多个进程可以把同一物理页映射到各自的虚拟地址。缺页中断（Page Fault）：访问的页不在物理内存时，CPU 触发缺页中断，操作系统从磁盘加载页到内存（或从 swap 换入）。物理内存不足时通过 LRU 等算法换出页面。虚拟内存是现代操作系统多任务运行的基础。

## 什么是死锁，死锁的条件与处理策略

死锁是多个进程互相持有对方需要的资源且都不释放，导致全部永久阻塞。必要条件：1) 互斥（Mutual Exclusion）：资源同一时刻只能被一个进程使用。2) 持有并等待（Hold and Wait）：进程持有资源的同时等待其他资源。3) 不可剥夺（No Preemption）：已分配的资源不能被强行夺走。4) 循环等待（Circular Wait）：多个进程形成资源等待环。处理策略：预防（破坏四个条件之一，如资源一次性申请、按序分配资源）、避免（银行家算法，判断分配后是否安全，实际很少用）、检测与恢复（检测资源分配图是否有环，有则终止进程或抢占资源，如数据库的锁超时）、鸵鸟策略（多数操作系统采用，死锁罕见、处理代价高，直接忽略让用户重启）。工程上最常见的是按固定顺序加锁和超时机制避免死锁。

## 阻塞 IO、非阻塞 IO、IO 多路复用、异步 IO

网络编程中 IO 模型的演进：1) 阻塞 IO（BIO）：进程调用 recv 后一直阻塞直到数据到达，一连接一线程，连接多了线程爆炸。2) 非阻塞 IO（NIO）：recv 立即返回，没有数据返回 EAGAIN，进程需要轮询，浪费 CPU。3) IO 多路复用（IO Multiplexing）：select/poll/epoll 一次监听多个 fd，内核通知哪些 fd 就绪再处理。epoll 用事件驱动 + 红黑树管理 fd，只返回就绪的 fd，支持百万连接，是 Nginx、Redis、Netty 的基石。4) 信号驱动 IO：数据到达时发信号通知。5) 异步 IO（AIO）：内核完成整个读写后通知，应用全程不阻塞，Linux 原生 AIO 支持不完善，实际常用 io_uring 或封装（如 Netty 的模拟异步）。阻塞与非阻塞是"调用者的视角"，同步与异步是"整个数据流动的视角"。Redis 单线程靠 epoll 支撑高并发就是这个模型的经典实践。

## 同步、异步、阻塞、非阻塞的区别

同步与异步关注"消息通信机制"：同步调用必须等结果返回才继续；异步调用发出请求后立即返回，结果通过回调、事件或状态轮询获取。阻塞与非阻塞关注"调用者等待时的状态"：阻塞调用时线程挂起等待；非阻塞调用立即返回，线程可以做其他事。组合：同步阻塞（传统 IO，简单但效率低）、同步非阻塞（轮询）、异步阻塞（少见，等待通知时阻塞）、异步非阻塞（最高效，事件驱动，如 Node.js、Netty）。举例：点外卖，同步=一直盯着手机等送达；异步=去做别的事，送达通知你；阻塞=等待时什么都干不了；非阻塞=等待时可以干别的。网络框架追求异步非阻塞，才能用少量线程支撑海量连接。

## 什么是负载均衡，四层和七层有什么区别

负载均衡把请求分发到多台后端服务器，提升系统吞吐和可用性（一台挂了请求自动转到其他台）。四层负载均衡（LVS、F5）：工作在传输层，基于 IP 和端口转发，不解析应用协议内容，性能极高（内核态转发，可达百万 QPS），适合 TCP/UDP 流量转发。七层负载均衡（Nginx、HAProxy）：工作在应用层，解析 HTTP 报文（URL、Header、Cookie），可以做更精细的路由（按路径分发到不同服务）、URL 重写、HTTPS 卸载、会话保持，性能低于四层但功能强大。七层负载均衡的实现：Nginx 反向代理收到 HTTP 请求后，按配置的 upstream 和后端转发。生产常见架构：四层 LVS/云 SLB 入口转发到 Nginx 集群，Nginx 按业务路由到后端应用。

## 什么是 cookie、session、token 的区别

HTTP 无状态，需要机制记住用户。Cookie：浏览器本地存储的小数据（由服务端 Set-Cookie 下发），每次请求自动携带，4KB 上限，可设 HttpOnly（防 JS 读取）和 Secure（仅 HTTPS 发送）。Session：服务端存储的会话数据，Session ID 通过 Cookie 传给浏览器（或 URL），服务端内存/Redis 保存用户状态，用户量大时占服务端资源。Token（JWT）：无状态认证，服务端签发包含用户信息和过期时间的签名令牌，客户端存储（本地存储/Cookie）后每次请求放在 Authorization 头，服务端验签即可，无需存会话，适合分布式和前后端分离。JWT 缺点：无法主动失效（要等过期）、体积大。选型：传统服务端渲染用 Session，前后端分离/移动端用 JWT，安全要求高可用短期 token + refresh token。Cookie 与 Token 是"凭证存放位置"的区别，Session 与 JWT 是"服务端有无状态"的区别。
