# 系统设计与架构面试题

## 如何设计一个短链接系统

短链接系统的核心是长链接到短码的映射。核心功能：生成短链接、重定向、统计访问量。数据存储：用 MySQL 或 Redis 存映射关系，短码作为主键。短码生成方式：1) 发号器（Snowflake、自增 ID 转 Base62，性能好，可预测）；2) 随机字符串加去重（碰撞概率低，无需发号器）。重定向：用 302 临时重定向（方便统计和修改目标链接，适合短链接跳转，回来后可以重新请求）或 301 永久重定向（浏览器缓存，统计不准）。高级功能：过期时间、自定义短链、访问统计（UV、PV、来源分析）。扩展：布隆过滤器防遍历攻击，CDN 缓存 302 响应，写入先放 Redis 异步落库。

## 如何设计一个支持高并发的点赞系统

点赞系统核心要求：高并发写入、防止重复点赞、读多写少。设计要点：1) 缓存层：用 Redis 的 Set 存每个用户点赞记录（Set 天然去重），用 Hash 或 String 存点赞总数。2) 点赞操作：SADD post_id user_id + INCR like_count，原子操作。3) 数据最终一致：定时或异步把 Redis 中的点赞数据刷回 MySQL，避免频繁写库。4) 防刷限制：同一用户对同一内容只能点赞一次（Redis 兜底去重），接入风控限制单用户频次。5) 读扩展：读 Redis 直接返回总数，MySQL 作为持久化备份。6) 取消点赞同理：SREM + DECR。数据量极大时，用异步队列解耦，Redis 崩溃时可从 MySQL 恢复。

## 如何设计一个实时排行榜

实时排行榜典型需求：百万用户、按分数实时排序、支持查看 Top N 和自己排名。Redis ZSet 天然适合：ZADD key score member 更新分数，ZREVRANGE 取 Top N，ZREVRANK 查排名。ZSet 底层是跳跃表 + 哈希表，增删改查 O(log N)，百万级轻松应对。数据持久化：定期把 ZSet 快照存到 MySQL，Redis 重启后恢复。如果分数相同需要按时间排序，可以把分数设计为"得分 + 时间戳后缀"（如 950.20260903），用 double 存储，整数部分为得分小数部分为时间戳反向。更高并发场景可做分区 ZSet 或写时合并缓存。

## 如何设计一个分布式 ID 生成器

分布式 ID 要求全局唯一、趋势递增、高可用、性能好、有时序。常见方案：1) UUID：128 位，本地生成无中心化，但太长不有序，不适合做数据库主键（B+ 树随机插入导致页分裂，性能差）。2) Snowflake 算法：64 位（1 位符号 + 41 位时间戳毫秒 + 10 位机器 ID + 12 位序列号），单机单毫秒可生成 4096 个 ID，趋势递增，适合做主键。问题是时钟回拨会导致 ID 冲突，解决：记录上次生成时间，回拨时等待或暂停服务。3) 数据库号段模式：批量取一段 ID 放内存用，用完再取，性能好，ID 递增。4) Redis INCR：简单但需额外维护 Redis。选型：业务 ID 用 Snowflake，数据库主键用号段模式。

## 如何设计一个 CDN 系统

CDN（内容分发网络）把静态资源缓存到离用户最近的边缘节点，用户就近获取，减轻源站压力。核心流程：用户请求资源 → DNS 解析到 CDN 的智能调度系统 → 调度系统按用户 IP 返回最近节点 IP → 用户请求该节点，节点有缓存直接返回，没有则回源站拉取并缓存。关键设计：1) 全局负载均衡（GSLB），基于用户 IP 和节点负载分配最优节点；2) 缓存策略，按文件类型、URL 模式设置 TTL（图片 30 天，HTML 几分钟）；3) 缓存预热，大促前主动把热资源推送到边缘节点；4) 缓存刷新，源站更新后主动失效 CDN 缓存。回源策略：若节点宕机逐级回落（同一区域→同运营商→全局源站）。

## 如何设计一个支付系统

支付系统核心是资金安全、防重、状态机。设计要点：1) 支付订单：支付订单号和业务订单号分离，支付订单包含金额、状态、渠道、过期时间。2) 支付状态机：待支付 → 支付中 → 支付成功 / 支付失败，状态单向流转，不可逆向。3) 防重：支付回调用唯一键（支付订单号 + 渠道流水号）去重，幂等处理。4) 对账：每天与渠道对账，核对自己和渠道的流水，不一致的标记差异人工处理。5) 退款：支持原路退回，金额校验，退款走独立订单。6) 安全：金额不可篡改（签名校验）、敏感信息加密（支付卡号、CVV）、HTTPS 传输。7) 高可用：支付链路上任何一环故障都要有降级方案，保证最终一致性。支付系统的核心原则：永远不要丢失或重复一笔钱。

## 如何设计一个消息推送系统

消息推送系统支持向海量用户推送消息（App 推送、短信、邮件、站内信）。核心流程：消息创建 → 受众筛选 → 任务分发 → 渠道投递 → 回执处理。设计要点：1) 消息模板化，通过模板变量生成个性化消息。2) 受众筛选，基于用户标签（性别、年龄、地区、行为）从用户画像系统筛选出目标用户列表，用位图存储用户 ID 集合降低内存。3) 任务拆分，按用户 ID 分片，多线程平行推送。4) 渠道适配器，封装推送通道（APNs、FCM、短信网关、邮件），统一接口，失败重试。5) 频率控制，同一用户短时间收到多条消息时合并或限速。6) 回执处理，推送结果（送达、已读、点击）异步回传，用于统计和效果分析。7) 补偿机制，失败任务进入死信队列，定时重试。

## 如何设计一个 API 网关

API 网关是系统对外的统一入口，处理所有的请求路由、认证、限流、日志、熔断等横切关注点。核心功能：1) 路由转发，根据请求路径将请求转发到对应后端服务，支持动态路由。2) 认证鉴权，统一校验 JWT Token、API Key，避免每个服务重复实现。3) 限流熔断，按用户/接口/IP 限流，后端超时或失败时快速熔断（Circuit Breaker），防止级联故障。4) 请求/响应转换，协议转换（HTTP 转 gRPC）、请求头改写、响应体裁剪。5) 日志与监控，全量请求日志、链路追踪、调用链耗时分布。6) 灰度发布，按用户比例/Cookie/IP 路由到不同版本的服务。实现方案：Kong（基于 Nginx + Lua）、Spring Cloud Gateway、Zuul。生产上网关必须是轻量无状态的，容易水平扩展。

## 什么是缓存穿透、缓存击穿、缓存雪崩

缓存穿透：查询一个不存在的数据，缓存和数据库都不命中，每次请求都打穿到数据库，可能导致数据库挂掉。解决方案：布隆过滤器拦截不存在 key，或缓存空值（短过期时间）。缓存击穿：一个热点 key 在缓存过期瞬间，大量并发请求同时打到数据库。解决方案：互斥锁（缓存重建时加锁，只有一个线程去查数据库回填缓存，其他等待），或设置热点 key 永不过期（后台异步更新）。缓存雪崩：大量 key 同时过期，或 Redis 宕机，大量请求直接打到数据库。解决方案：过期时间加随机值打散、集群部署（Redis 主从 + Sentinel/Cluster）、本地缓存（Caffeine）做二级缓存降级、限流保护数据库。三个问题本质都是"缓存失效时如何保护数据库"。

## 微服务架构下如何进行服务发现

服务发现解决微服务实例动态变化（扩缩容、故障、重启）时，消费者如何找到可用实例的问题。两种模式：客户端发现（Consumer 直接从注册中心拉取实例列表，负载均衡策略客户端实现，如 Eureka + Ribbon、Nacos）和服务端发现（Consumer 请求负载均衡器，由它转发到实例，如 Kubernetes Service + kube-proxy、Consul + Nginx）。注册中心的核心功能：服务注册、心跳（健康检查）、服务下线通知、缓存。选型：Eureka（AP 原则，强调可用性，停止维护但有替代品）、Consul（CP 原则，强调一致，自带健康检查和 KV 存储）、Nacos（阿里，支持 AP/CP 切换，功能丰富）、Kubernetes（云原生场景下直接使用 Service 和 Ingress，应用层无需关心注册中心）。
