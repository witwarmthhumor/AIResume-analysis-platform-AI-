# AI 应用开发核心知识

## 大语言模型 LLM 的核心概念：Token、上下文窗口、Temperature、Top-p

大语言模型（Large Language Model，LLM）的本质是一个基于海量文本训练的"下一个词预测器"：给定一段输入文本，模型输出下一个 Token 的概率分布，再通过采样策略选出一个 Token，如此循环直到生成结束符或达到最大长度。理解 LLM 应用开发必须先掌握四个核心概念。

第一是 Token。Token 是模型处理文本的最小单位，不是字也不是词。英文中一个 Token 大约是 4 个字符或 0.75 个单词，中文由于字符密度高，一个汉字通常占 1-2 个 Token。API 调用的计费、输入输出长度限制都以 Token 为单位。开发时需要估算 Token 用量：可以用 tiktoken 等库精确计算，也可以粗略按"中文每字约 1.5 Token、英文每词约 1.3 Token"估算。

第二是上下文窗口（Context Window）。模型能同时处理的最大 Token 数，包括输入 Prompt 和输出回复。例如 gpt-3.5-turbo 是 4K/16K，gpt-4 是 8K/32K，一些新模型达到 128K 甚至 1M。超出上下文窗口的内容会被截断或报错。RAG 的核心价值之一就是在有限的上下文窗口内，只把最相关的信息塞进去，而不是把整个知识库都传给模型。

第三是 Temperature（温度）。控制生成的随机性，取值 0 到 2。Temperature 越低，输出越确定、越保守，适合事实性问答、代码生成、数据提取等需要准确的场景；Temperature 越高，输出越多样、越有创造性，适合写诗、头脑风暴、创意写作。实践建议：知识问答类设 0.3-0.5，创意类设 0.7-1.0，绝对不要设 0（可能导致重复和退化）。

第四是 Top-p（核采样）。另一个控制随机性的参数，取值 0 到 1。Top-p 从概率最高的 Token 开始累加，直到累积概率达到 p，然后只在这个候选集合里采样。例如 Top-p=0.9 意味着只考虑累积概率达到 90% 的那些 Token。Top-p 和 Temperature 通常配合使用，一般建议改一个就好，不要同时大幅调整两者。Top-k 则是只保留概率最高的前 k 个 Token，原理类似。

## Prompt Engineering 提示词工程：零样本、少样本、思维链、角色设定、结构化输出

Prompt Engineering 是 AI 应用开发中性价比最高的技能——不需要改模型、不需要训练，只通过优化输入文本就能显著提升输出质量。核心技巧有五类。

第一是零样本（Zero-shot）和少样本（Few-shot）。零样本就是直接给任务描述，让模型回答，适合简单任务。少样本是在 Prompt 里给出几个"输入-输出"的示例，让模型模仿格式和风格，适合需要特定输出格式或复杂推理的任务。少样本的示例要多样化、覆盖边界情况，示例的质量比数量更重要，3-5 个精心设计的示例通常比 10 个随便写的效果好。

第二是思维链（Chain of Thought，CoT）。让模型"先思考再回答"，而不是直接给结论。最简单的方式是在 Prompt 末尾加一句"请一步步思考"或"Let's think step by step"。CoT 能显著提升数学题、逻辑推理、多步决策类任务的准确率，因为模型把中间推理过程写出来后，最终结论的错误率会降低。更高级的变体包括 Self-Consistency（多次采样取多数答案）和 Tree of Thoughts（探索多条推理路径）。

第三是角色设定（Role Prompting）。在 Prompt 开头告诉模型"你是一个资深 Java 后端工程师"或"你是一个严格的代码审查员"，能让模型的回答风格、专业深度、关注点都贴合角色。角色设定要具体，不要只说"你是一个专家"，而要说"你是一个有 10 年经验的 Java 后端工程师，熟悉 Spring Boot、MySQL 优化和分布式系统，回答时优先给出可运行的代码示例"。

第四是结构化输出。在 AI 应用中，模型输出通常需要被程序解析，所以必须要求结构化格式。最常用的是 JSON：在 Prompt 里明确指定 JSON 的字段名、类型、含义，并给出一个示例。也可以要求 Markdown 表格、固定模板、XML 标签等。关键是格式约束要写在 Prompt 的显眼位置，最好在最后重复一遍"请严格按照上述 JSON 格式输出，不要输出额外文字"。对于关键应用，建议在代码层对模型输出做 JSON 解析和校验，解析失败时重试或降级。

第五是 Prompt 的组织结构。一个好的 Prompt 通常按以下顺序组织：角色设定 → 任务描述 → 背景信息/上下文 → 输出格式要求 → 示例（少样本）→ 约束条件。把最重要的指令放在开头和结尾（模型对开头和结尾的注意力更高），中间放细节。避免在一个 Prompt 里塞太多互相矛盾的指令，复杂任务拆成多步调用或用 Agent 分步完成。

## RAG 检索增强生成：原理、完整流程、为什么需要 RAG、RAG vs 微调

RAG（Retrieval-Augmented Generation，检索增强生成）是目前构建企业级 AI 应用最主流的架构。它的核心思想是：模型本身的知识是静态的、有截止日期的、可能幻觉，而企业内部知识是动态的、私有的、海量的；RAG 在用户提问时，先从外部知识库检索出最相关的几段内容，把这些内容作为上下文塞进 Prompt，再让模型基于检索到的内容回答问题。

完整的 RAG 流程分为离线和在线两个阶段。离线阶段（入库）：1) 收集原始文档（PDF、Word、txt、网页等）；2) 文本提取与清洗（去掉格式标签、页眉页脚、重复内容）；3) 文本切块（Chunking），把长文档切成 300-800 字的小块，块之间留 10%-20% 的重叠；4) 对每个块调用 Embedding 模型生成向量；5) 把向量和原文存入向量数据库（如 pgvector、Chroma、Milvus）。在线阶段（问答）：1) 用户提问；2) 对问题做 Embedding；3) 在向量数据库中做相似度检索，找出 Top-K 个最相关的块（通常 K=3-5）；4) 把检索到的块拼接成上下文，连同用户问题一起组成 Prompt；5) 调用 LLM 生成回答；6) （可选）在回答中标注引用来源。

为什么需要 RAG？三个核心原因。第一是知识时效性：LLM 的训练数据有截止日期，不知道最新的产品文档、公司政策、实时数据。RAG 从外部知识库实时检索，知识永远是最新的。第二是私有知识：企业内部文档、客户数据、技术手册不可能放进训练集，RAG 可以在推理时动态注入。第三是减少幻觉：模型基于检索到的真实内容回答，而不是凭记忆编造，准确率和可溯源性大幅提升。

RAG vs 微调（Fine-tuning）是常见的选型问题。微调是用特定数据继续训练模型，改变模型的参数和行为风格；RAG 是在推理时检索外部知识，不改变模型。选型原则：如果需要模型掌握新的事实性知识（产品文档、政策法规、技术手册），用 RAG；如果需要改变模型的输出风格、语气、格式（比如模仿某个作家的写作风格、学习特定的代码规范），用微调；两者可以结合——RAG 负责知识，微调负责风格。成本上，RAG 的入库和检索成本远低于微调，且知识更新只需重新入库，不需要重新训练，维护性更好。

## Embedding 向量与相似度检索：什么是 Embedding、余弦相似度、向量数据库

Embedding（嵌入/向量化）是 RAG 的基石。简单说，Embedding 就是把一段文本转换成一个高维浮点数向量（例如 768 维或 1536 维），这个向量代表了文本的语义含义——语义相近的文本，向量在高维空间中距离也近。

Embedding 模型的输入是文本，输出是固定维度的向量。常见的 Embedding 模型包括 OpenAI 的 text-embedding-ada-002（1536 维）、text-embedding-3-small（1536 维）、BAAI 的 bge 系列、以及可以本地部署的 nomic-embed-text（768 维）、all-MiniLM 等。选择 Embedding 模型时要考虑：维度（维度越高表达力越强但存储和计算成本越高）、中文支持（很多英文模型对中文效果差，要选多语言或中文优化的模型）、部署方式（云端 API 方便但有数据隐私和成本问题，本地模型免费但需要 GPU 或接受 CPU 推理速度）。

相似度计算最常用的是余弦相似度（Cosine Similarity）。两个向量 A 和 B 的余弦相似度 = (A·B) / (|A| × |B|)，即两个向量夹角的余弦值，取值范围 -1 到 1。值越接近 1 表示语义越相似，越接近 0 表示无关，负值表示语义相反。余弦相似度的优势是不受向量长度影响——长文本和短文本只要语义相近就能匹配。除了余弦相似度，还有内积（Dot Product）和欧氏距离（L2 Distance），具体用哪种取决于向量数据库的索引类型和 Embedding 模型的训练方式。大多数 Embedding 模型默认用余弦或内积。

向量数据库是专门存储和检索高维向量的数据库。它的核心能力是"近似最近邻搜索"（ANN）——在百万级甚至亿级向量中，毫秒级找出与查询向量最相似的 Top-K 个。常见的向量数据库包括：pgvector（PostgreSQL 扩展，适合已有 PG 栈的项目，用 HNSW 或 IVFFlat 索引）、Chroma（轻量级，适合原型和中小规模）、Milvus（分布式，适合大规模生产）、Weaviate、Pinecone（云端托管）等。向量数据库通常同时存储向量和原始文本（以及元数据如文档 ID、标题、来源），检索时返回原始文本供 LLM 使用。

## 文本切块 Chunking：为什么要切块、切块策略、块大小与重叠的选择

切块（Chunking）是 RAG 离线阶段最关键也最容易被忽视的一步。为什么要切块？三个原因：第一，Embedding 模型有最大输入长度限制（通常 256-8192 Token），超长文档无法直接向量化；第二，检索时返回的块要放进 LLM 的上下文窗口，块太大会占用过多 Token，块太小又会丢失上下文；第三，检索的粒度——如果把一整篇文档作为一个块，检索到的内容太宽泛，模型无法定位到具体答案；如果切成句子级，又会丢失句子之间的逻辑关系。

切块策略有多种。最常用的是固定长度切块（Fixed-size Chunking）：按固定字符数或 Token 数切，块之间留重叠。简单可靠，适合大多数场景。第二种是语义切块（Semantic Chunking）：先按句子或段落切，计算相邻块的语义相似度，在相似度低的地方分割——保证每个块内部语义连贯。效果更好但实现复杂、计算成本高。第三种是结构化切块：根据文档的固有结构切，比如 Markdown 按标题（#、##、###）切，代码按函数切，PDF 按页切。适合结构清晰的文档。实践中最常用的是"固定长度 + 按段落边界对齐"——先按段落分割，再把小段落合并到目标长度，避免在句子中间切断。

块大小（Chunk Size）的选择是一门权衡艺术。块太小：每个块信息不足，检索到的内容无法支撑完整回答，且块数量多导致检索噪声大。块太大：单个块包含多个主题，检索精度下降，且占用 LLM 上下文 Token 多。经验值：通用知识问答用 300-500 字（约 500-800 Token），代码或技术文档用 400-800 字，长文档摘要用 800-1200 字。最佳块大小需要通过评测集（黄金问答对）实际测试——用不同块大小跑检索，看 hit@K 和回答准确率，选最优值。

重叠（Overlap）是指相邻两个块之间共享的内容长度，通常设为块大小的 10%-20%。重叠的作用是防止关键信息被切断在两个块的边界上——比如一个完整的定义或推理过程刚好跨在块边界，没有重叠的话两个块都不完整。重叠过大则浪费存储和计算，且检索时可能返回高度重复的块。一般建议重叠 50-100 字，或块大小的 15%。

## AI Agent 与工具调用：Function Calling、ReAct 范式、Agent 与普通对话的区别

AI Agent（智能体）是 LLM 应用的高级形态。普通的 LLM 对话是"一问一答"——用户给输入，模型给输出，模型不能主动做任何事。Agent 则是让 LLM 具备"思考-行动-观察-再思考"的循环能力，可以主动调用外部工具（搜索、数据库查询、代码执行、API 调用），根据工具返回的结果继续推理，直到完成任务。

Function Calling（函数调用/工具调用）是实现 Agent 的基础机制。OpenAI 兼容协议的 Function Calling 工作流程：1) 开发者在 API 请求中定义一组工具（函数）的 JSON Schema，包括函数名、参数描述、参数类型；2) 模型根据用户问题决定是否调用工具、调用哪个工具、传什么参数——模型不直接执行工具，而是输出一个特殊的 tool_calls 字段，包含要调用的函数名和参数；3) 开发者的后端程序解析 tool_calls，实际执行对应的函数（比如查数据库、调搜索 API、跑代码）；4) 把工具执行结果作为 tool message 传回给模型；5) 模型基于工具结果生成最终回答。Function Calling 的关键是模型只做"决策"，实际执行由开发者的代码完成，这样既安全又可控。

ReAct（Reasoning + Acting）是 Agent 最经典的工作范式。ReAct 的每一步循环包括三个部分：Thought（思考——模型分析当前状态，决定下一步做什么）、Action（行动——调用一个工具）、Observation（观察——工具返回的结果）。模型不断重复"思考→行动→观察"，直到认为任务完成，输出最终答案。ReAct 的优势是可解释性强——每一步的思考和行动都可见，出问题时能定位是哪一步决策错了。ReAct 适合需要多步推理和工具调用的复杂任务，比如"帮我查一下公司最近三个月的销售额，画个趋势图，然后写一段分析"——需要查数据库、画图、写分析三步。

Agent 与普通对话的核心区别有三点。第一是自主性：普通对话模型只回答，Agent 能主动规划和执行多步任务。第二是工具使用：普通对话没有外部工具，Agent 可以调用搜索、数据库、代码执行、API 等工具。第三是状态管理：Agent 需要维护任务状态（已完成什么、正在做什么、下一步做什么），通常用一个 scratchpad 或消息历史记录每一步的 Thought/Action/Observation。但 Agent 不是万能的——简单任务用普通对话或单次 Function Calling 就够了，Agent 的循环会增加延迟和 Token 消耗，且可能陷入无限循环或错误决策，需要设置最大步数和错误处理。

## 流式输出 SSE：为什么 AI 应用要用流式输出、SSE 的实现原理与注意事项

流式输出（Streaming）是 AI 应用用户体验的关键。LLM 生成回答是逐 Token 进行的，如果等全部生成完再一次性返回，用户可能要等 5-30 秒看到一片空白，体验极差。流式输出让模型每生成几个 Token 就推送给前端，用户能看到文字逐字打出，感知延迟大幅降低。

SSE（Server-Sent Events，服务器推送事件）是实现流式输出最常用的技术。SSE 是 HTTP 协议的一部分，基于 HTTP 长连接，服务器可以主动向客户端推送数据，而不需要客户端反复轮询。SSE 的特点：单向通信（只能服务器推给客户端，客户端不能通过同一连接发数据）、基于纯文本（数据格式简单，Content-Type 为 text/event-stream）、自动重连（连接断开后浏览器自动重连）、支持事件类型和 ID。与 WebSocket 相比，SSE 更简单、基于 HTTP、不需要额外的协议升级，适合 AI 回答这种"服务器单向推送文本"的场景；WebSocket 是双向的，适合需要客户端实时发数据的场景（如协作编辑、游戏）。

SSE 的实现原理。后端：设置响应头 Content-Type: text/event-stream、Cache-Control: no-cache、Connection: keep-alive；然后循环调用 LLM 的流式接口，每收到一段 Token 就按 SSE 格式写入响应体——格式是 "data: {JSON数据}\n\n"，每段数据以两个换行结尾；可以用 "event: {事件名}" 标注事件类型（如 start、delta、end、error）；生成结束后发送 "data: [DONE]\n\n" 或关闭连接。前端：用 EventSource API 或 fetch + ReadableStream 读取 SSE 流；解析每段 data，把 Token 追加到页面上，实现打字机效果；处理 end 事件关闭连接，处理 error 事件重连或报错。

实现流式输出的注意事项。第一是反向代理缓冲：Nginx 默认会缓冲响应，导致 SSE 数据被攒在一起一次性发送，必须设置 proxy_buffering off 和 proxy_cache off。第二是超时：长连接可能被中间层超时断开，设置合理的 proxy_read_timeout（如 300s）。第三是错误处理：流式过程中模型报错，要通过 error 事件推给前端而不是直接断开，前端要能处理中途错误。第四是 Token 计数：流式模式下要在结束时统计总 Token 用量（prompt_tokens + completion_tokens），用于计费和限流。第五是前端渲染：逐 Token 追加时要注意 Markdown 实时渲染的性能，可以用 requestAnimationFrame 节流，避免每来一个 Token 就重渲染整个页面。

## AI 应用典型架构：RAG 应用的前后端分离设计、关键组件与数据流

一个生产级的 RAG AI 应用通常采用前后端分离架构，分为前端、后端、AI 服务层、数据存储层四个部分。

前端（Frontend）：用户交互界面，通常用 Vue、React 等框架。核心组件包括：聊天界面（消息列表、输入框、发送按钮）、流式渲染（逐 Token 打字机效果 + Markdown 渲染）、引用来源展示（回答中标注引用了哪些文档块，点击可跳转）、知识库管理（文档上传、列表、删除）、历史会话管理。前端不直接调用 LLM API（避免暴露 API Key 和跨域问题），所有 AI 请求走后端。

后端（Backend）：业务逻辑层，通常用 FastAPI（Python）、Spring Boot（Java）、Express（Node.js）等。核心模块包括：认证授权（用户注册登录、JWT/Session、权限控制）、对话管理（会话创建、消息存储、历史恢复）、RAG 检索服务（接收问题→Embedding→向量检索→拼接 Prompt→调用 LLM→流式返回）、知识库管理（文档上传、文本提取、切块、异步入库、删除）、用量统计与限流（记录每次调用的 Token 用量、按用户/IP 限流）、后台任务（用 Celery 或类似框架异步处理文档入库，避免阻塞 HTTP 请求）。

AI 服务层（AI Service）：封装 LLM 和 Embedding 的调用。核心设计是"模型无关"——定义统一的接口（如 chat(messages, temperature, stream) → 生成器、embed(texts) → 向量列表），底层可以切换不同的模型提供商（OpenAI、Anthropic、通义千问、DeepSeek、本地 Ollama）。切换模型只需要改配置，不需要改业务代码。AI 服务层还要处理：API Key 管理（从环境变量读取，不写死在代码里）、重试与降级（调用失败时指数退避重试，或切换备用模型）、Token 计数与计费、请求超时控制、内容安全过滤（可选，对输入输出做敏感词检测）。

数据存储层（Data Storage）：通常包括关系型数据库（PostgreSQL/MySQL，存用户、会话、消息、文档元数据、用量日志）、向量数据库（pgvector/Chroma/Milvus，存文档块的向量和原文）、缓存（Redis，存会话状态、限流计数、热点检索结果）、对象存储（MinIO/S3，存上传的原始文档文件）、消息队列（Redis/RabbitMQ，用于异步任务如文档入库）。小型项目可以用 PostgreSQL + pgvector + Redis 三件套搞定，不需要引入太多组件。

完整的问答数据流：用户在前端输入问题 → 前端 POST 到后端 /api/chat → 后端认证用户 → 后端调用 AI 服务层的 embed 对问题向量化 → 在向量数据库检索 Top-K 相关块 → 把检索结果和历史消息拼接成 Prompt → 调用 LLM 流式接口 → 后端通过 SSE 把 Token 逐段推给前端 → 前端逐字渲染 → 生成结束后后端保存消息到数据库、记录 Token 用量 → （可选）在回答中返回引用来源。

## 模型选型与 API 调用：OpenAI 兼容协议、换模型的成本、限流与重试、Key 管理

模型选型是 AI 应用开发的重要决策。目前主流的 LLM API 几乎都兼容 OpenAI 的接口格式（OpenAI Compatible API），包括 DeepSeek、通义千问（DashScope）、智谱 GLM、Moonshot、本地 Ollama 等。这意味着统一用 OpenAI SDK 或兼容的 HTTP 客户端，只需要改 base_url、api_key、model 三个配置项就能切换模型，业务代码零改动。

选型时要考虑五个维度。第一是能力：不同模型在推理、代码、中文、长上下文等方面各有优劣，要用自己的实际任务做评测，不要只看排行榜。第二是速度：首 Token 延迟（TTFT）和生成速度（Tokens/秒）直接影响用户体验，交互式聊天建议 TTFT < 1 秒。第三是成本：按输入/输出 Token 单价计算预估成本，输出 Token 通常比输入贵 2-3 倍，RAG 应用因为有检索上下文，输入 Token 较多。第四是上下文窗口：需要长文档处理的场景选 128K 以上的模型，普通问答 8K-32K 足够。第五是数据隐私：企业敏感数据不要发到第三方 API，考虑本地部署模型（如 Ollama + Llama/Qwen）或私有云部署。

API 调用的工程实践。第一是 Key 管理：API Key 绝对不能写在代码里或提交到 Git，必须放在环境变量（.env 文件）或密钥管理服务中，后端从环境变量读取；.env 要加入 .gitignore；前端永远不直接持有 LLM 的 API Key，所有调用走后端代理。第二是限流（Rate Limiting）：对每个用户或 IP 限制调用频率（如每分钟 20 次、每天 100 次），防止滥用和恶意刷接口；用 Redis 的滑动窗口或令牌桶算法实现。第三是重试（Retry）：API 调用可能因网络波动、服务端过载失败，用指数退避重试（第一次等 1 秒，第二次 2 秒，第三次 4 秒），最多重试 2-3 次；但 4xx 错误（如 401 未授权、400 参数错误）不要重试，直接报错。第四是超时：设置合理的请求超时（如 60 秒），避免请求挂死；流式输出的超时要更长（如 300 秒）。第五是降级：主模型调用失败时，可以自动切换到备用模型（如主用 DeepSeek，备用通义），保证服务可用性。

换模型的成本评估。因为 OpenAI 兼容协议的存在，切换模型的代码成本几乎为零，但实际成本包括：重新测试（不同模型的输出风格、格式遵从度不同，要重新跑测试集验证）、调整 Prompt（某些模型对 Prompt 的敏感度不同，可能需要微调提示词）、Embedding 模型联动（如果换了 Embedding 模型，向量维度可能变化，需要重新生成所有向量并重建索引——这是 RAG 应用换模型最大的隐性成本）、成本重新核算（不同模型单价差异大，要重新评估月度成本）。建议在 AI 服务层设计时就把 LLM 模型和 Embedding 模型的配置分开，支持独立切换。

## RAG 评测与优化：黄金问答集、检索质量指标、幻觉问题、常见优化手段

RAG 应用上线后不能只靠"感觉效果不错"，必须用可量化的指标评测和持续优化。核心评测方法是构建黄金问答集（Golden Q&A）——人工整理一批有代表性的问题和标准答案（或标准文档来源），覆盖常见问题、边界问题、长尾问题，然后用这套题批量测试 RAG 系统，用指标量化效果。

检索质量的核心指标。第一是 Hit Rate（命中率）：对于每个问题，标准答案所在的文档块是否出现在检索返回的 Top-K 结果中。Hit@K = 命中的问题数 / 总问题数。例如 Hit@5=90% 表示 90% 的问题在 Top5 结果中能找到正确答案来源。第二是 MRR（Mean Reciprocal Rank，平均倒数排名）：不仅看是否命中，还看命中的位置——正确块排在第 1 位得 1 分，第 2 位得 0.5 分，第 3 位得 0.33 分，取所有问题的平均值。MRR 比 Hit Rate 更严格，因为它奖励把正确答案排在前面。第三是 Precision（精确率）：检索返回的块中有多少是相关的。第四是 NDCG（归一化折损累计增益）：考虑相关性分级和位置的综合指标。实践中最常用 Hit@K 和 MRR，简单直观。

回答质量的评测。检索好不代表回答好，还要评测最终回答的准确性。方法包括：人工评分（1-5 分，评估准确性、完整性、相关性）、LLM-as-Judge（用另一个更强的 LLM 作为评委，自动评分）、事实一致性检查（检查回答中的每个事实陈述是否能在检索来源中找到依据）、引用准确率（回答中标注的引用是否真的支撑对应内容）。关键是要区分"检索失败"（正确的块没检索到）和"生成失败"（检索到了正确内容但模型回答错了），两者的优化方向完全不同。

幻觉（Hallucination）是 RAG 应用最头疼的问题——模型编造检索来源中不存在的信息。缓解手段：第一是 Prompt 约束，明确告诉模型"只能基于以下参考资料回答，如果资料中没有相关信息，请回答'根据现有资料无法回答'，不要编造"；第二是引用溯源，要求模型在回答中标注每个结论的引用来源，方便用户核对；第三是检索增强，提高 Top-K 数量、优化检索质量，确保正确信息在上下文中；第四是后处理校验，用代码或另一个 LLM 检查回答中的事实是否都能在来源中找到，发现幻觉时重试或标注；第五是模型选型，能力强的模型幻觉率更低。

常见优化手段。检索侧：调整块大小和重叠（用评测集找最优值）、换更好的 Embedding 模型、用混合检索（向量检索 + 关键词检索 BM25 加权融合，即 RRF）、加查询改写（用 LLM 把用户的口语化问题改写成更适合检索的查询）、加元数据过滤（按文档类型、日期、作者等预过滤）。生成侧：优化 Prompt（角色设定、输出格式、约束条件）、调整 Temperature（知识问答降低到 0.3）、用更好的模型、加多轮追问（回答不完整时让模型继续补充）。系统侧：加缓存（相同问题直接返回缓存答案）、异步预计算（热门问题提前检索好）、用户反馈闭环（让用户点赞/点踩，用反馈数据优化检索和 Prompt）。
