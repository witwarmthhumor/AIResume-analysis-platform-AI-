# Java 核心面试题库

## synchronized 和 ReentrantLock 的区别

synchronized 是 JVM 层面的关键字，由 JVM 自动加锁释放锁，使用简单，出现异常会自动释放。ReentrantLock 是 java.util.concurrent 包提供的 API 锁，需要手动 lock() 和 unlock()，通常配合 try-finally 使用。ReentrantLock 相比 synchronized 的优势：支持公平锁、支持中断响应、支持尝试获取锁 tryLock、支持多个条件变量 Condition。在 JDK 6 之后 synchronized 引入了锁升级（偏向锁、轻量级锁、重量级锁）后，两者性能差距已不大。建议：简单场景用 synchronized，需要高级特性（可中断、公平、多条件）时用 ReentrantLock。

## volatile 关键字的作用与限制

volatile 修饰的变量保证可见性：一个线程修改后，其他线程能立即看到新值，它通过内存屏障禁止指令重排序实现。volatile 不保证原子性：例如 i++ 这种读改写操作不是原子的，多线程下仍会丢更新。适用场景：作为状态标志位（如布尔开关）、双重检查锁中的单例实例变量。volatile 不能替代锁，只适合"一个线程写、多线程读"或"写入不依赖当前值"的场景。

## HashMap 的底层原理

HashMap 底层是数组 + 链表 + 红黑树。JDK 1.8 起，当链表长度超过 8 且数组长度超过 64 时，链表转红黑树，降低查询复杂度从 O(n) 到 O(log n)。默认初始容量 16，负载因子 0.75，当元素数量超过 容量*负载因子 时触发扩容，扩容为原来的 2 倍。HashMap 不是线程安全的，多线程下 put 可能丢数据或死循环（JDK1.7 头插法扩容）。线程安全场景用 ConcurrentHashMap，它采用 CAS + synchronized 锁住单个桶（Node 数组的每个槽位），并发度远高于 HashTable。

## ConcurrentHashMap 的线程安全实现

JDK 1.8 的 ConcurrentHashMap 放弃了分段锁，改为 CAS + synchronized 锁桶头节点。put 时先用 CAS 尝试把新节点放进空桶，若桶非空则对该桶头节点加 synchronized 锁后操作，锁粒度细到单个桶，不同桶可以并发写。size() 通过 CounterCell 数组累加避免竞争。读操作不加锁，靠 volatile 修饰的节点数组和 Node 的 val/next 保证可见性。相比 HashTable（全局一把锁），并发度提升显著。

## JVM 内存区域的划分

JVM 运行时数据区分为线程私有和线程共享。线程私有：虚拟机栈（每个方法调用对应一个栈帧，存局部变量表、操作数栈）、本地方法栈、程序计数器。线程共享：堆（对象实例，GC 主要区域，可细分新生代/老年代）、方法区（类元信息、常量池、静态变量，JDK8 由元空间 Metaspace 实现，使用本地内存）。栈溢出对应 StackOverflowError，堆内存不足对应 OutOfMemoryError。

## GC 垃圾回收算法与分代回收

常见回收算法：标记-清除（有碎片）、复制算法（新生代使用，From/To 区互换）、标记-整理（老年代使用，压缩内存）。分代回收：对象优先在 Eden 区分配，经过 Minor GC 且存活则晋升到 Survivor 区，达到一定年龄后晋升老年代。老年代回收称 Major GC/Full GC。常用收集器：新生代 ParNew、老年代 CMS（并发标记清除）、G1（把堆分成 Region，可预测停顿时间，JDK9 起默认）。

## 类的加载过程

类加载分为加载、链接（验证、准备、解析）、初始化三个阶段。加载：通过全限定名读取字节码生成 Class 对象。验证：校验字节码合法性。准备：为静态变量分配内存并设置默认值（如 0、null）。解析：把常量池中的符号引用替换为直接引用。初始化：执行静态变量赋值和静态代码块。类加载器：引导类加载器（Bootstrap，加载 JDK 核心类）、扩展类加载器、应用类加载器，采用双亲委派模型——先让父加载器尝试加载，避免核心类被重复加载和被篡改。

## Spring Bean 的生命周期

Spring 容器中 Bean 的完整生命周期：实例化（构造器或工厂方法创建对象）→ 属性填充（依赖注入）→ 初始化前（BeanPostProcessor 的 postProcessBeforeInitialization）→ 初始化（afterPropertiesSet 或 init-method）→ 初始化后（postProcessAfterInitialization，AOP 代理在此阶段生成）→ 使用 → 销毁（destroy-method）。核心扩展点：BeanPostProcessor 在初始化前后各回调一次，Spring 的 AOP、事务等大量功能基于它实现。

## Spring 事务的传播行为

事务传播行为定义了方法调用时事务如何传递。常用：REQUIRED（默认，有事务则加入，无则新建）、REQUIRES_NEW（总是新建事务，挂起外层）、NESTED（嵌套事务，基于 Savepoint 可部分回滚）、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER。注意：Spring 事务默认只对 RuntimeException 回滚，受检异常不会回滚，除非显式配置 rollbackFor。事务失效的常见原因：方法自调用（this 调用不走代理）、方法不是 public、类没有被 Spring 管理、异常被 catch 吞掉。

## 什么是索引，为什么要用索引

索引是一种帮助数据库快速定位数据的结构，类似书的目录。没有索引时查询需要全表扫描 O(n)，有索引后可以按索引结构定位 O(log n) 甚至更快。MySQL InnoDB 默认使用 B+ 树索引：叶子节点存数据、非叶子节点只存索引键，树更矮更宽，单次磁盘 IO 就能跨越更多层。索引能显著加速查询，但会占用额外空间、拖慢写入（每次增删改都要维护索引），所以不是越多越好。覆盖索引（查询列都在索引里）能避免回表。

## MySQL 的聚簇索引与非聚簇索引

InnoDB 的聚簇索引：表数据本身按主键组织，主键索引的叶子节点直接存整行数据，一张表只有一个聚簇索引。二级索引（非聚簇）的叶子节点存主键值，查询时通过二级索引找到主键，再回表查数据，这个回表过程叫回表查询。如果二级索引已经包含查询所需的所有列（覆盖索引），就无需回表，这是覆盖索引优化的原理。主键建议用自增整数或有序 UUID，避免随机插入导致页分裂。

## MySQL 的隔离级别

SQL 标准定义四个隔离级别：读未提交（READ UNCOMMITTED，可能脏读）、读已提交（READ COMMITTED，解决脏读，可能不可重复读）、可重复读（REPEATABLE READ，解决不可重复读，可能幻读）、串行化（SERIALIZABLE，全部串行）。MySQL InnoDB 默认是可重复读，并通过 MVCC 快照读 + 间隙锁解决幻读：普通查询是快照读（读历史版本），当前读（select for update）用 next-key lock 锁住范围防止幻行插入。MVCC 通过 undo log 保存多版本，ReadView 控制可见版本。

## Redis 的数据结构与使用场景

Redis 核心数据结构：String（缓存、计数器、分布式锁的 value）、Hash（对象字段存储，省内存）、List（消息队列、最新列表）、Set（去重、共同好友）、ZSet（排行榜、带权重的有序集合）。Redis 单线程模型（命令执行单线程，IO 多路复用）保证原子性，单条命令天然原子。持久化两种：RDB（定时快照，恢复快但可能丢数据）和 AOF（追加日志，可配 everysec/always 策略）。缓存常见问题：缓存穿透（查不存在的数据，用布隆过滤器）、缓存击穿（热点 key 过期，用互斥锁）、缓存雪崩（大量 key 同时过期，加随机过期时间）。

## Redis 分布式锁的实现

Redis 分布式锁的经典实现：SET key value NX PX 30000 原子地"不存在才设置并设过期时间"，避免超时死锁。value 用唯一标识（如 UUID），释放时用 Lua 脚本先校验再删除，防止误删别人刚获取的锁。锁的过期时间要大于业务执行时间，否则业务没跑完锁就释放了（可用看门狗续期）。分布式锁的极端场景（主节点故障、锁丢失）Redis 官方方案是 Redlock，但业界普遍认为其仍有争议，可用 Zookeeper/etcd 做强一致分布式锁。

## TCP 三次握手与四次挥手

三次握手建立连接：客户端发 SYN，服务端回 SYN+ACK，客户端再回 ACK，双方确认收发能力后建立连接。为什么是三次：两次不够（无法确认客户端收到了服务端的 SYN），四次多余。四次挥手断开连接：主动方发 FIN，被动方回 ACK（半关闭），被动方处理完再发 FIN，主动方回 ACK 后等待 2MSL 才关闭。为什么等 2MSL：确保最后一个 ACK 能被对方收到，且让本连接的历史报文在网络中消失，避免干扰新连接。TIME_WAIT 过多可用 tcp_tw_reuse 缓解。

## HTTP 与 HTTPS 的区别

HTTP 是明文传输，HTTPS 在 HTTP 下加了 SSL/TLS 加密层，默认端口从 80 变 443。HTTPS 建立连接需要 TLS 握手：客户端发支持的加密套件，服务端返回证书，客户端用 CA 公钥验证证书真实性，然后协商出对称密钥（用非对称加密安全传递），之后用对称加密传输数据。HTTPS 解决了三个问题：防窃听（加密）、防篡改（完整性校验）、防冒充（证书验证）。代价是握手多两轮 RTT、加解密消耗 CPU。现代网站基本全站 HTTPS。

## HTTP 缓存机制

HTTP 缓存分为强缓存与协商缓存。强缓存：响应头 Cache-Control（max-age 秒数）或 Expires，命中则直接用本地副本不发请求。协商缓存：资源过期后带 If-None-Match（对应 ETag）或 If-Modified-Since（对应 Last-Modified）发请求，服务端判断未变化则返回 304，不返回 body。优先级：Cache-Control 优先于 Expires，ETag 优先于 Last-Modified。应用场景：静态资源（图片、JS、CSS）用强缓存加文件名 hash，接口数据用协商缓存或不用缓存。

## TCP 与 UDP 的区别

TCP 是面向连接的可靠传输：三次握手建立连接、确认重传、流量控制（滑动窗口）、拥塞控制（慢启动、拥塞避免），保证数据有序不丢不重。UDP 是无连接不可靠传输：不握手、不确认、不重传，但头部开销小（8 字节）、延迟低、支持广播组播。适用场景：TCP 用于 HTTP、文件传输、邮件等需要可靠性的场景；UDP 用于实时音视频、游戏、DNS 查询等对实时性要求高、可容忍少量丢失的场景。TCP 可靠性以复杂度和延迟为代价。

## DNS 解析过程

DNS 将域名解析为 IP。过程：浏览器先查本地 DNS 缓存 → 查 hosts 文件 → 向配置的 DNS 服务器（递归查询）发请求 → 该服务器从根域名服务器开始逐级向下查询（迭代查询）→ 找到目标域名的权威服务器 → 返回 IP。常见记录类型：A（IPv4）、AAAA（IPv6）、CNAME（别名）、MX（邮件）。实际应用会做多级缓存（浏览器、操作系统、本地 DNS、各级缓存）减少根服务器压力。一次解析通常有 10~100ms 开销，所以 CDN 和 HTTP/2 都大量用 DNS 预解析和连接复用。

## 什么是微服务，与传统单体相比的优缺点

微服务把单体应用拆成一组小服务，每个服务独立部署、独立伸缩、独立数据库，通过 API 通信。优点：模块解耦、可按服务独立扩展、技术栈可以异构、故障隔离、小团队并行开发效率高。缺点：分布式复杂度高（网络不可靠）、服务间调用延迟、数据一致性难保证（分布式事务）、运维成本高（监控、链路追踪、部署编排）、调试排障更困难。所以微服务不是银弹，业务复杂度和团队规模不够时，模块化单体是更务实的选择。

## 分布式系统最终一致性的常见方案

分布式环境无法做到强一致的"实时一致"，常用最终一致性方案：本地消息表（事务写业务库和消息表，后台任务投递）、消息队列 MQ（异步解耦，生产者发消息，消费者幂等消费）、TCC 事务（Try-Confirm-Cancel 三段式）、Saga（长事务拆成多个本地事务+补偿）。关键点是幂等性：消息可能重复投递，消费端必须幂等（用唯一键、状态机、去重表）。选择标准：对一致性要求高选 TCC/Saga，能接受短暂不一致选 MQ 异步最终一致，性能要求高就放松一致性。

## CAP 定理与 BASE 理论

CAP 定理：分布式系统无法同时满足一致性 Consistency、可用性 Availability、分区容错性 Partition tolerance 三个中的两个以上。网络分区必然存在，所以实际是在 C 和 A 之间取舍：CP（如 Zookeeper、etcd，分区时优先保证一致）与 AP（如大多数缓存、消息队列场景，分区时优先保证可用）。BASE 理论是 CAP 在实践中的落地：基本可用（Basically Available）、软状态（Soft state）、最终一致（Eventually consistent），即不追求强一致，允许中间状态，最终收敛一致。

## 常见的负载均衡策略

负载均衡把请求分发到多台服务器。常见策略：轮询（Round Robin，依次分发，权重轮询支持按机器性能配权重）、最少连接（Least Connections，发给当前连接数最少的机器，适合长连接场景）、IP Hash（同一客户端 IP 固定打到同一台机器，解决 session 粘性问题，但节点增减会影响命中）、一致性哈希（把请求按哈希环分布，节点增删只影响少量 key 的映射，适合分布式缓存）。实现层面：LVS（四层）、Nginx（七层）、云负载均衡。选择看业务：无状态服务用轮询+权重，有状态服务用一致性哈希。

## 为什么要用消息队列

消息队列的核心价值是解耦、异步、削峰。解耦：生产者和消费者不需要知道对方存在，只依赖消息协议，系统间通过 MQ 通信互不影响。异步：请求发完消息就返回，耗时操作（发短信、生成报表）异步执行，提升响应速度。削峰：高并发瞬时流量（如秒杀）先入队，消费端按能力慢慢处理，保护下游数据库不被冲垮。代价：系统多了 MQ 组件增加运维，引入消息可靠性问题（丢失、重复、乱序），需要保证生产者可靠发送、消费者幂等消费。常见选型：Kafka（吞吐高，日志/大数据场景）、RabbitMQ（功能全，可靠性好）、RocketMQ（阿里，事务消息）。

## 如何设计一个秒杀系统

秒杀系统核心是"削峰限流 + 提前减库存 + 异步化"。分层设计：前端层（静态化秒杀页、按钮置灰、验证码）、网关层（限流，如令牌桶、漏桶，限制并发）、应用层（用 Redis 预减库存，Lua 保证原子性，防止超卖）、消息队列（下单请求入队异步落库）、数据库（乐观锁/唯一键保证最终扣减不超卖）。关键点：库存热点，用 Redis 分片或分段扣减避免单 key 热点；幂等，防止重复下单；数据最终一致，缓存与数据库异步同步。用户体验上"秒杀开始"以 Redis 为准，落库结果异步通知。

## 数据库与缓存一致性如何保证

缓存与数据库的一致性经典问题是：先更新数据库还是先删缓存，以及并发下的读写竞态。推荐"先更新数据库，再删缓存"（Cache Aside 模式）：更新数据库后删除缓存，下次读时缓存未命中从库加载回填。为什么删而不是更新缓存：避免并发写导致缓存与库不一致，删除成本低。风险窗口：删除缓存瞬间有并发读会把旧值回填，可通过"延迟双删"或"对删除加短暂过期"缓解。对一致性要求高的场景，可用 binlog 订阅（Canal）异步删除缓存，把一致性交给消息机制，避免业务代码耦合。

## 什么是 B+ 树，为什么 MySQL 用它做索引

B+ 树是平衡多叉搜索树，特点：非叶子节点只存索引键不存数据，叶子节点存全部数据并通过指针相连形成有序链表。相比 B 树：B+ 树非叶子节点能存更多键，树更矮，磁盘 IO 次数更少；叶子节点有序链表天然支持范围查询和排序（B 树范围查询要中序遍历）。相比 Hash 索引：B+ 树支持范围查询、前缀匹配、排序，而 Hash 只支持等值查询。相比二叉树：B+ 树高度低（几百万数据也就 3~4 层），一次 IO 读一个磁盘页能装更多键。所以 InnoDB 用 B+ 树做索引。

## MySQL 慢查询优化的一般步骤

慢查询优化步骤：1) 开启慢查询日志定位慢 SQL（long_query_time 设置阈值）；2) 用 EXPLAIN 分析执行计划，重点看 type（是否全表扫描 ALL）、key（是否走索引）、rows（扫描行数）、Extra（是否 filesort、临时表）；3) 检查索引：是否缺索引、索引列的顺序是否匹配查询条件、是否发生隐式类型转换或函数导致索引失效；4) 优化 SQL：避免 select *、避免在索引列上用函数、分页优化（用游标/主键范围代替大 offset）；5) 必要时改表结构（冗余字段、拆分大表）或加缓存。原则：先看执行计划再动手，一次只改一个变量并对比。

## Redis 过期删除与内存淘汰策略

Redis 删除过期 key 的策略：惰性删除（访问时才判断是否过期）与定期删除（每隔一段时间随机抽取部分过期 key 删除）结合。内存达到 maxmemory 时的淘汰策略：allkeys-lru（淘汰最久未使用，常用）、volatile-lru（仅对设了过期时间的 key）、allkeys-random、volatile-random、volatile-ttl（优先淘汰剩余寿命短的）、noeviction（不淘汰直接报错）。生产建议：allkeys-lru 或 volatile-lru，并给热数据合理设置过期时间。缓存雪崩可以通过给过期时间加随机值避免大量 key 同时失效。

## 常见的分布式事务解决方案

分布式事务跨多个数据库或服务，无法用单库 ACID 解决。方案：1) 两阶段提交 2PC：准备阶段所有参与者预提交，提交阶段统一提交，有协调者，阻塞式、性能差、协调者单点；2) TCC：Try（预留资源）-Confirm（确认提交）-Cancel（回滚），无锁、性能好，但业务侵入大，每个操作要写三段逻辑；3) Saga：长事务拆成多个本地事务，失败逐个补偿，适合流程长、可补偿的场景；4) 本地消息表 + MQ：事务内写消息表，异步投递，最终一致。实际项目常用 TCC 或 MQ 方案，纯 2PC 因阻塞问题较少直接用。

## 如何理解 TCP 的粘包和拆包问题

TCP 是字节流协议，没有消息边界，应用层多条消息可能被合并在一个报文里（粘包）或被拆成多个报文（拆包）。原因：发送方可能一次 write 多次或接收方读缓冲一次性读走多包。解决方案：1) 消息定长（固定长度，不足补位）；2) 在消息头加长度字段（Length+Body，如 Netty 的 LengthFieldBasedFrameDecoder）；3) 用特殊分隔符（如 \n、\r\n）分割；4) 用应用层协议如 HTTP/2 的帧、protobuf 自带长度前缀。设计网络协议时一般用"长度字段 + 二进制内容"最通用可靠。

## 线程池的核心参数与执行流程

Java 线程池（ThreadPoolExecutor）核心参数：corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime（非核心线程空闲存活时间）、workQueue（任务队列）、threadFactory（线程工厂）、RejectedExecutionHandler（拒绝策略）。执行流程：1) 线程数 < corePoolSize → 创建核心线程执行；2) 线程数 >= corePoolSize → 任务进队列等待；3) 队列满且线程数 < maximumPoolSize → 创建非核心线程执行；4) 队列满且线程数 = maximumPoolSize → 执行拒绝策略（AbortPolicy 抛异常 / CallerRunsPolicy 调用者执行 / DiscardPolicy 丢弃）。拒绝策略选 CallerRunsPolicy 较安全，避免任务静默丢失。

## 什么是死锁，如何避免

死锁是多个线程互相持有对方需要的锁且互不释放，导致全部永久阻塞。产生死锁的四个必要条件：互斥、持有并等待、不可剥夺、循环等待。避免方法：1) 破坏循环等待——按固定顺序加锁（所有线程按相同顺序获取锁）；2) 破坏持有并等待——一次性申请所有锁（不现实）；3) 破坏不可剥夺——用 tryLock 带超时获取锁，获取不到就释放已有锁重试；4) 破坏互斥——用无锁数据结构（原子类、CopyOnWrite）。实际最常用的是"顺序加锁 + 超时获取"。定位死锁可用 jstack 导出线程栈查看 "Found one Java-level deadlock"。

## 为什么说 String 是不可变的

String 底层是 final char[] 数组且类本身是 final 的，无法被继承或修改内容。不可变带来好处：1) 线程安全（不可变对象天然并发安全）；2) 字符串常量池可以共享引用（String a="x", String b="x" 指向同一对象），节省内存；3) 用作 HashMap 的 key 或哈希缓存时值不会变化，hashCode 可缓存。字符串拼接用 + 在循环里会不断创建新对象，应改用 StringBuilder（线程不安全）或 StringBuffer（线程安全）。String.intern() 可以把运行期字符串放入常量池。

## Java 的集合框架体系

Java 集合框架两大分支：Collection 与 Map。Collection 下分 List（有序可重复：ArrayList 数组实现查快增删慢、LinkedList 链表实现、Vector 线程安全）、Set（不可重复：HashSet 哈希实现、LinkedHashSet 保插入序、TreeSet 红黑树保有序）、Queue（ArrayDeque、PriorityQueue 优先队列）。Map 下有 HashMap、LinkedHashMap、TreeMap、Hashtable、ConcurrentHashMap。判断标准：是否需要有序、是否允许重复、是否线程安全、增删查频率。掌握每个实现的数据结构（数组/链表/哈希/树）就掌握了选择依据。

## 面向对象设计的六大原则

SOLID + 最少知识原则：单一职责 SRP（一个类只做一件事）、开闭原则 OCP（对扩展开放、对修改关闭，用抽象和多态扩展）、里氏替换 LSP（子类必须能替换父类且行为正确）、接口隔离 ISP（接口尽量小，客户端不依赖用不到的接口）、依赖倒置 DIP（依赖抽象不依赖具体实现）、迪米特法则 LoD（最少知道原则，降低类间耦合）。实践落地：多用接口定义行为、组合优于继承、依赖注入解耦。设计模式的选用也应服务于这些原则而非为了用而用。

## Spring AOP 的实现原理

AOP（面向切面编程）把横切逻辑（日志、事务、权限）从业务代码中抽出。Spring AOP 基于动态代理：目标类实现接口时用 JDK 动态代理（java.lang.reflect.Proxy，代理类实现相同接口）；目标类没有接口时用 CGLIB 代理（生成目标类的子类，通过继承覆盖方法）。代理对象在方法调用前后织入通知（前置 @Before、后置 @After、环绕 @Around、异常 @AfterThrowing）。实现核心是 BeanPostProcessor：容器初始化后检测切面，为匹配的 Bean 生成代理对象替换原对象。注意：自调用（this.xxx）不经过代理，切面不生效；final 方法无法被 CGLIB 代理。

## 为什么 MySQL 默认使用可重复读

MySQL InnoDB 默认隔离级别是可重复读，原因：1) 历史原因，MySQL 的 binlog 基于语句复制，读已提交级别下可能出现主从不一致（网上经典论述），可重复读配合 next-key lock 能保证语句级一致；2) 通过 MVCC 实现快照读可重复读，配合当前读的间隙锁（next-key lock）解决了幻读，实际上在可重复读级别下业务已经感受不到幻读。所以 InnoDB 在可重复读下既保证了可接受的一致性，又保持了较好的并发性能。串行化级别全部加锁、并发极差，生产基本不用。

## 如何实现一个限流器

限流保护系统不被突发流量打垮。常见算法：1) 固定窗口计数（每分钟一个窗口，到上限就拒绝，缺点是窗口边界突刺）；2) 滑动窗口（把窗口细分多格，精确统计，实现略复杂）；3) 漏桶（请求进桶按固定速率流出，能削峰但无法应对突发）；4) 令牌桶（按速率放令牌，取到令牌才放行，允许一定突发，应用最广）。落地方式：单机用 Guava RateLimiter / 本地计数；分布式用 Redis（INCR + 过期时间做固定窗口，或 Lua 脚本实现令牌桶）。限流维度：按 IP、按用户、按接口。超限响应 429 并带重试提示。

## 什么是消息幂等，如何保证

幂等指同样的操作执行多次结果一致。分布式场景消息可能重复投递（网络重传、消费者重启重试），所以消费者必须幂等。保证手段：1) 唯一键去重：消费前查去重表（订单号、消息 ID），已处理过则跳过；2) 数据库唯一约束：利用唯一索引让重复插入报错后捕获忽略；3) 状态机：业务记录有状态流转，只有符合前置状态才处理；4) 乐观锁版本号：更新时 where version=期望值。设计原则：让业务操作的天然幂等键（订单号、用户ID+时间）落库，避免在代码里做内存级去重（重启就失效）。

## 简述一次完整的 HTTP 请求经历了什么

用户在浏览器输入 URL 回车后：1) DNS 解析域名得到 IP；2) 建立 TCP 连接（三次握手）；3) 若是 HTTPS 先 TLS 握手协商密钥；4) 浏览器构造 HTTP 请求报文（请求行、请求头、请求体）发送；5) 经过可能存在的代理、负载均衡、CDN 转发；6) 到达服务器，Web 服务器（Nginx）把请求交给应用（如 Spring、FastAPI）；7) 应用处理业务、查询数据库/缓存、生成响应；8) 响应经原路返回，浏览器解析渲染（HTML/CSS/JS）；9) 若连接可复用（Keep-Alive/HTTP2）则保留连接，否则四次挥手关闭。这个链路每一环都可能成为性能瓶颈，全链路追踪正是为此而生。

## 如何理解 MySQL 的 MVCC

MVCC（多版本并发控制）让读写不互相阻塞。实现核心：每行数据有隐藏列 trx_id（最后修改事务 ID）和 roll_pointer（指向 undo log 中旧版本）；事务执行快照读时生成 ReadView（记录活跃事务列表），判断某版本是否对当前事务可见：版本提交时间早于 ReadView 且不在活跃列表则可读，否则沿 undo log 找更早版本。读已提交级别每次查询生成新 ReadView，可重复读级别事务内复用同一个 ReadView，这就是两种隔离级别下快照读结果不同的原因。MVCC 只对快照读生效，当前读（for update）仍需加锁。

## 常见的设计模式及应用场景

创建型：单例（配置类、线程池，饿汉/懒汉/双重检查锁）、工厂（根据类型创建对象，解耦创建逻辑）、建造者（复杂对象分步构建，如 Lombok @Builder）。结构型：代理（AOP、远程调用、延迟加载）、装饰器（Java IO 流包装，动态加功能）、适配器（接口兼容，如 JDBC 驱动）。行为型：观察者（事件监听、消息通知）、策略（算法可替换，如支付方式选择）、模板方法（流程骨架固定、细节延迟到子类，如 JdbcTemplate）。实际项目中设计模式不是目的，解决具体问题、可读性优先，模式是为可维护性服务的工具。

## 如何排查 JVM 内存泄漏

内存泄漏是对象无法被回收但不再使用，持续堆积最终 OOM。排查步骤：1) 观察现象：Full GC 频繁、老年代持续增长、最终 OutOfMemoryError；2) 用 jps 找进程，jmap -heap 看堆概况；3) jmap -dump 导出堆快照（.hprof）；4) 用 MAT（Memory Analyzer）或 VisualVM 分析快照：看支配树找大对象，看类直方图定位占用最多的类；5) 结合业务代码定位引用链（GC Roots 分析）找出谁持有这些对象。常见泄漏点：静态集合只增不减、未关闭的连接/流/监听器、ThreadLocal 不 remove、缓存无淘汰策略。修复后要复现验证。

## 为什么需要 ThreadLocal，会有什么问题

ThreadLocal 为每个线程保存独立的变量副本，实现线程隔离，常用于：数据库连接、Session、请求上下文、SimpleDateFormat（非线程安全）等。实现原理：每个 Thread 有一个 ThreadLocalMap，以 ThreadLocal 为 key 存值。隐患：线程池场景下线程复用，若不调用 remove()，ThreadLocal 的值会一直残留在线程里，可能造成内存泄漏（key 是弱引用，value 是强引用，key 被回收后 value 无法访问却占内存）和业务串数据。所以规范是：ThreadLocal 用完必须在 finally 里 remove()，或使用 try-with-resources 封装。

## Spring 如何解决循环依赖

循环依赖指 A 依赖 B、B 又依赖 A。Spring 通过"三级缓存"解决单例 Bean 的 setter/字段注入循环依赖：一级缓存（成品单例）、二级缓存（提前暴露的半成品）、三级缓存（存 ObjectFactory 工厂）。流程：创建 A 时先实例化（未完成属性注入）放入三级缓存，A 注入 B 触发创建 B，B 注入 A 时从三级缓存拿到 A 的提前引用（半成品）完成 B，B 创建完成，A 继续注入 B 完成创建。注意：构造器注入无法解决循环依赖（实例化阶段就需要对方），会直接报错，所以推荐构造器注入时避免循环依赖，或改用 setter/字段注入。Spring Boot 2.6 起默认禁止循环依赖。
